# リポジトリ文書の整備

[ドキュメントの更新](../../DEVELOPMENT.md#ドキュメントの更新)を判断基準にし、今回の読者が必要な説明へ辿れる状態にする。このリポジトリの文書整備に使い、元の依頼の範囲と公開権限を引き継ぐ。

1. 対象checkoutのREADME・開発方針と、依頼に関係するIssue・差分を読み、読者・困り事・範囲を特定する。要求や方針が未確定なら[clarify-requirements](../clarify-requirements/SKILL.md)で整理する。合意済みの範囲は聞き直さず、単独変更もIssueへ紐づける。
2. 今回影響する説明とその参照元を選び、コード・設定・実行入口・対象版の検証結果に照合する。既存の正本への更新か、更新不要かを判断する。根拠の不足と未合意の判断を区別し、依存する記述を保留する。
3. 選んだ正本を現在の説明として更新し、重複や古い参照を整理する。経緯と検証記録は既存の保存先へ参照を残す。文書と実装の不一致からコードの変更が必要と分かった場合は、Issueの範囲を確認して実装担当へ戻す。
4. 共通方針の完了条件に照らして、関連するリンク・例・コマンド・保証範囲を確認する。実装に伴う更新では、その実装の検証・独立評価へ渡し、別の検証ループを追加しない。単独変更は既存の共通checkとレビュー方針に従う。
5. 更新した正本と理由、実際の確認結果、残る事項を既存のPR説明または依頼の完了報告にまとめる。公開を依頼されていなければローカル成果物として返す。未実施の独立評価・公開確認・人の承認を完了扱いにしない。
