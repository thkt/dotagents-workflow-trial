# 情報・合意・証拠の設計案

[OUTCOME](OUTCOME-draft.md)、[開発方針](development-policy-draft.md)、[概念と責任範囲](architecture-concepts.md)に基づく検討用の設計案。GitHubを必須とする前提で情報配置を提案する。工程名・エージェント構成・実行方式は未決定であり、現行実装やGitHub上の運用を変更しない。

## 判断に必要な情報

| 判断 | 必要な情報 |
| --- | --- |
| 何を解決するか | 困りごと、利用場面、望む変化、実現する価値。 |
| どの解決を選ぶか | 現状の根拠、原因、制約、選択肢、不確実性。 |
| どこまで進めてよいか | 合意した要求・対象外・品質基準・完了条件、変更や公開の権限。 |
| 成果が適切か | 対象の変更、検証結果、レビュー指摘と対応、残る制約。 |
| 次に何をするか | 未解決事項、その影響、必要な判断や行動、中断時の再開条件。 |

これは必須書式や工程の一覧ではない。必要な情報がすでにあれば参照して使い、不足に応じて調査・対話・実装・検証を行う。事実・仮説・提案・合意・実行結果を区別する。

## GitHub上の配置案

| 情報 | 主な配置先 | 重複を避ける扱い |
| --- | --- | --- |
| 作業ごとの目的、要求、対象外、完了条件 | Issue本文 | 現在の合意内容を読む入口とする。相談中・提案中の内容を合意済みと混同しない。 |
| 重要な判断、合意、要求変更の理由 | Issueの会話記録 | 判断対象と根拠を残し、合意後に本文を更新する。本文の最新状態だけで過去の合意を説明しない。 |
| 変更内容、理由、成果の確認方法、残る制約 | Pull Request本文 | Issueを参照し、要求全文を複製しない。 |
| コードに対するレビュー指摘と対応 | Pull Requestのレビュー記録 | 実行ログとは分け、対応した変更または採用しない根拠を辿れるようにする。 |
| 検証の実行結果、画面・操作の証拠 | CIや必要な成果物の記録 | PRから要点と参照先を示す。生ログを本文へ繰り返し貼らない。ローカル検証も対象と条件を明示する。 |
| 継続して使う方針・設計理由・実装例 | リポジトリ内の文書・コード・テスト | 作業固有の履歴はIssue/PR、現在使う知識は適切な既存ファイルへ反映する。 |
| 試行錯誤、進行・再開に必要な一時情報 | 作業環境内の記録 | 外部共有に必要な結論と根拠を選び、すべてを公開記録にしない。具体的な保存方式は別途設計する。 |

変更の大小を問わず、変更作業にはIssueを必須とする。これはチームがGitHub上で目的・合意・進行状況・結果を確認できるようにするための決定である。コード・テスト・設定・ドキュメントの小さな変更も対象とし、PRだけで要求の記録を代替しない。

要求の正本はIssue本文とする。大きな仕様を文書で管理する場合は、Issueが参照する対象版を明確にし、同じ要求を両方で編集しない。合意した範囲に含まれる変更は既存Issueへ紐づけ、修正やcommitごとに別Issueを作らない。記述量は変更に合わせるが、目的・範囲・完了条件を省略しない。

Issueには作業開始・重要な進展・判断待ち・中断・結果が分かる情報を残し、PRや証拠へ辿れるようにする。全操作の逐次投稿は求めず、以下の共有タイミングに沿って更新する。具体的な投稿・同期の実装方式は未決定とする。PRや新規文書の作成は成果に応じて判断し、「変更不要」の結論に空のPRを作らない。変更を伴わない相談をいつIssueへ記録するかは、この決定とは分けて扱う。

長期保存が必要な証拠については、保持期間とアクセス条件を設計・導入時に確認する。参照先が失われた場合は、以前の成功記録と、現在確認できる証拠を区別する。

## 要求定義で合意済み資産を再利用する

Issueを作る時点から、合意済み資産の適用条件・品質基準・検証方法を参照する。部品の採用で今回の目的や期待する結果まで決まるとは扱わない。共通の条件は本文へ複製せず、今回固有の条件と差分を明示する。

一覧検索パターンを使う場合の記載例は次のとおり。これは仮想例であり、現在のリポジトリに合意済み資産が存在するという意味ではない。

| Issueに残すもの | 例 |
| --- | --- |
| 目的 | 商品一覧から対象の商品を見つけられるようにする。 |
| 適用する資産・合意 | 一覧検索パターンの対象版、合意の根拠、適用条件への参照。 |
| 今回固有の条件 | 商品名・商品コードを検索対象とする。 |
| 差分・対象外 | 保存済み検索は追加しない。共通条件からの変更があれば明示する。 |
| 完了の確認 | 適用する共通検証に加え、今回の検索対象と画面への接続を確認する。 |

Issueと参照先を合わせて、今回適用される完了条件を読めるようにする。参照先は版を特定し、更新によって合意済み要求が黙って変わらないようにする。参照不能、適用条件外、共通条件と今回の要求の矛盾があれば、実装前に必要な調査・判断を行う。複数の資産を組み合わせる場合、その組み合わせ自体が共通の合意でカバーされるかも確認する。

共通条件の参照は、今回の利用について必要な検証を実行しなくてよいという意味ではない。省けるのは条件の重複記載・再合意と、適用範囲内で確認済みの観点の再評価である。要求定義・実装・検証・レビューが同じ合意を参照する。

## Issueでの共有内容と更新タイミング

操作ログではなく、チームの判断や引き継ぎに必要な変化を共有する。この共有方針は合意事項とし、定期投稿の間隔や新しい状態ラベル一式を必須にはしない。

| タイミング | 共有する内容 |
| --- | --- |
| 作業開始 | 目的、担当、合意範囲、完了条件。 |
| 重要な変更 | 方針・範囲・見通しの変更と理由。提案と合意済み変更を区別する。 |
| 判断待ち・中断 | 未解決事項、必要な判断、再開条件。 |
| レビュー依頼 | PR、今回確認してほしい観点、検証・画面などの証拠への参照。 |
| 終了 | 達成結果、残る制約、関連PR・知見への参照。未達で停止した場合は、その結果を完了と区別する。 |

目的・要求・完了条件は本文を正本とし、変更理由や重要な進展は会話記録に残す。PRにあるレビュー観点や検証の詳細は、Issueから要点と参照先を示し、全文を複製しない。既存の記録で現在の状態が分かる場合は、同じ内容を追加投稿しない。

担当の交代時は、現在の到達点、未解決事項、次の行動と根拠へ辿れるようにする。記録した予定と、実際に確認できた結果を区別する。共有の更新は合意内容の変更や承認を意味しない。

## 合意の記録と権限

会話で得られた有効な合意は再利用し、GitHubへ記録するためだけに再承認を求めない。一方、合意の対象・内容・ユーザーの判断を追跡できるようにする。会話を外部へ記録する際は、必要な判断内容に絞り、公開に適さない情報を転記しない。

作業内容への合意と、Issue作成・push・PR作成・マージ・リリースなどの外部操作の許可は同一とは限らない。既存の許可範囲で実行し、不足する許可が必要になった時点で確認する。Issue本文の編集、ラベル、チェック欄、AIの要約だけからユーザーの合意を推定しない。

## 要求が変わったとき

変更提案と現在の合意を区別する。合意範囲内の実装選択は自律的に進める。再合意が必要な変更は、理由・影響・推奨案を示し、その判断に依存する作業を保留する。独立して進められる作業は継続できる。

合意後は現在の要求を更新し、変更の影響を受ける実装・レビュー・検証を特定する。実行中にIssueが編集されても、進行中の作業へ無条件に新しい要求を適用しない。編集が合意済み変更なのか、提案や誤記修正なのかを確認する。

どの要求を根拠に、どの成果物を評価したかを識別できるようにする。要求の対象版を保持する具体的な方法は、必要な追跡性を満たす最小の方式を選び、現段階では専用スキーマや二重の正本を導入しない。

## 変更と証拠の対応

| 変更されたもの | 再確認すること |
| --- | --- |
| 目的・要求・完了条件 | 既存の実装と検証が新しい合意を満たすか。 |
| コード・設定 | 影響する動作の検証とレビュー。 |
| テスト | テスト自体の妥当性と、対象コードでの実行結果。 |
| ドキュメント | 記述の正確さ、コードや合意内容との整合性。 |
| 実行環境・依存関係 | 過去の結果が新しい条件でも成立するか。 |

証拠には、何を、どの条件で確認したかを結びつける。コードでは対象commit、未commitの変更がある場合はその変更も特定できる必要がある。commitが同じだけで環境や要求も同じとは扱わない。

過去の結果は履歴として残す。変更後にも有効かは影響範囲から判断し、根拠が不十分なら再検証する。必須の完了チェックとして毎回必要な検証は、再利用の判断で省略しない。細かな証拠再利用の仕組み自体が再実行より高コストなら、単純に再実行する。

## 進行と完了

次の作業は不足している情報や証拠に応じて選ぶ。事実不足は調査、要求の矛盾は再検討・再合意、実装の不備は修正、環境不足は環境の整備、根拠の弱い指摘は再評価につなぐ。

LLMが次の行動を判断する場合も、権限、必須検証の実行、対象との対応、未解決事項による完了制限は、観測できる条件に基づいて制御する。意味的な品質判断を、単なるチェック欄の埋まり具合へ置き換えない。

完了・公開・マージ・リリースは区別する。Issueのクローズだけを品質の証拠とせず、利用後に評価する効果が残る場合は、その確認方法を明示する。新たな固定工程や状態一覧は、具体例で必要性を確認してから定める。

## ケースによる机上点検

以下は設計上の机上点検であり、実装の動作確認や品質・効率の実測結果ではない。追加する扱いは設計案として記載する。

| ケース | 最小の進め方 | 防ぐべき抜け・過剰処理 |
| --- | --- | --- |
| 曖昧な画面改善の相談 | 利用場面と原因を調べ、選択肢と完了条件を合意してから必要な変更を行う。 | 最初に挙がった解決策を、そのまま実装要求として固定しない。調査記録や比較資料は判断に必要な範囲に留める。 |
| 原因と修正範囲が明確な不具合 | 既存の要求と再現を確認し、原因に対する修正と回帰検証を行う。 | すでにある調査・合意を再作成しない。症状が消えただけで根本解決としない。 |
| 文書のみの変更 | 意味を変えるかを確認し、記述・参照・関連コードとの整合性を評価する。 | 無関係なE2Eや動画を要求しない。手順の変更なら、その手順の実行確認が必要かを判断する。 |
| 調査で変更不要と分かる | 根拠、適用条件、残る制約を説明し、依頼目的に沿った結論を得る。 | 空のPRを作らない。既存Issueがあれば結論をそこへ残し、閉じる操作は許可に従う。 |
| 実装中に要求が変わる | 提案と合意済み変更を区別し、影響を受ける作業と証拠を再評価する。 | 合意前に範囲を広げない。無関係な作業や証拠まで一律に破棄しない。 |
| 中断後にコードやIssueが変わっている | 保存した対象と現在の状態を比較し、差分の影響と権限を確認してから再開する。 | 古い根拠で継続しない。他者の変更を上書きしない。問題がなければ、再開だけを理由に再承認を求めない。 |
| PR作成などの外部操作が応答不明で中断する | 外部の実際の状態を確認してから、必要な操作だけを行う。 | 応答がないことを失敗と断定して、公開や作成を重複実行しない。確認できなければ、その操作に依存する進行を保留する。 |
| レビュー指摘が誤り、または好みの問題である | 要求・具体例・コードを根拠に妥当性を評価し、対応または不採用理由を残す。 | 全指摘を無条件に実装しない。実装者の自己申告だけで重要な指摘を解消済みにもしない。 |
| テストは成功するが、重要な誤実装を検出できない | 具体的な失敗条件からテストを評価し、必要なら誤実装を注入するなどして検出力を確かめる。 | 成功件数を品質と同一視しない。すべての変更に網羅的なmutation testingを義務化しない。 |
| CIや証拠へのアクセスが一時的に失われる | 確認済みの事項と確認できない事項を区別し、必要な証拠の回復または再検証を待つ。 | 確認不能を合格にもコード不良にも変換しない。独立して進められる作業まで止めない。 |

### 点検から具体化する扱い

1. 変更作業には大小を問わずIssueを用意し、合意範囲に対応する既存Issueがあればそこを使う。要求の正本をPRへ分散させず、目的・進行・結果をGitHub上でチームが追跡できるようにする。
2. 再開では、保存した作業状態だけでなく、現在のコード・要求・外部操作の結果を照合する。変更があったこと自体を失敗とはせず、その影響に応じて継続・修正・再合意を選ぶ。
3. 独立性は、別の名前のエージェントがいることではなく、要求と対象成果物を実装者の説明とは別に確かめられることで評価する。説明は補助として使い、レビュー対象と根拠への直接アクセスを確保する。
4. 検証手段は変更とリスクに応じて選ぶ。ただしリポジトリで必須と定めたチェックの例外を、その場のLLM判断だけで作らない。
5. 記録には現在の判断と次の行動が分かる情報を残す。専用の状態管理層、指摘台帳、合意ファイルを先に増やさず、既存の記録で不足する場合に限り追加を検討する。

これらのケースからは、固定工程を増やす必要性はまだ導けない。一方、要求と証拠の対象を特定すること、外部操作の結果を照合すること、意味的な評価の独立性は、具体的な実行構成で検証すべき条件になる。

## 検証・レビュー・人の判断の分担案

以下は設計上の分担案であり、実装済みの保証ではない。仕事の責任を示すもので、別々のエージェントや固定工程を必須にしない。

| 対象 | 主に担うもの | 確認内容と限界 |
| --- | --- | --- |
| 機械的に判定できる規則 | 静的解析・型検査など | 設定された規則への違反を検出する。規則に合うことだけで設計や意味の正しさを保証しない。 |
| 実行時の動作 | 自動テスト・必要な操作確認 | 合意した期待と失敗条件を確かめる。成功例だけで境界条件や競合時の正しさを結論づけない。 |
| 要求・解決方針の妥当性 | LLMによる評価と必要な人の判断 | 目的との対応、矛盾、対象外、検証可能性を確認する。優先順位や許容リスクを人に代わって変更しない。 |
| 成果物の意味的な品質 | 実装の自己確認から独立したLLMレビュー | 原因の解消、要求達成、保守性、不要な実装・契約、テストの検出力、文書と説明の整合性を評価する。判断理由と未確認事項を残す。 |
| 完了に必要な証拠の充足 | 観測可能な条件を確認する制御 | 必須検証の結果と対象、レビューの有無と未解決事項、権限を確認する。LLMの意味的な見落としを、この制御だけで解消できるとは扱わない。 |
| 目的・範囲・品質基準・重要なリスクの選択 | 権限を持つチームメンバー | 選択肢、根拠、影響、推奨案を受けて判断する。すでに有効な合意・権限があれば繰り返し確認しない。 |

Oxlintと、Biomeの `noExcessiveCognitiveComplexity` のみを使う方針は維持する。具体的な設定・対象・閾値は設計時に確認する。テストに関する静的規則は、検出できる具体的な欠陥に絞る。「価値のあるテストか」という判断全体を、件数・カバレッジ・複雑度の数値へ置き換えない。

### 独立したレビューに渡すもの

合意した要求の対象版、評価する変更と関連コード、適用する品質基準、検証の実行結果へ直接アクセスできるようにする。実装者の説明や既知の懸念は補助として使う。関連情報を選び、無関係な会話履歴をすべて引き継ぐことを必須にはしない。

レビュー対象は評価中に黙って変更しない。変更された場合は、評価対象と現在の成果物の差を確認して、必要な再評価を行う。レビュアーが対象コードや完了条件を書き換えて自分の指摘を成立・解消させる構成は避ける。必要な実行確認は、対象を保全できる環境で行う。

要求の評価ではユーザーの望む結果と判断材料を、成果物の評価では最終的な変更と証拠を使う。両者を同じチェックリストで代用しない。

### 指摘から次の行動へ

指摘には問題の箇所・条件、根拠、影響を示す。再現できる問題は再現結果を優先し、仮説は仮説として明示する。必須の保存スキーマを増やす前に、人が読んで対応を判断できる記録とする。

- 合意範囲内の不備は、修正して影響する検証・評価をやり直す。
- 誤った指摘は、反証や要求との照合で採否を決める。実装者の「対応不要」という宣言だけでは重要な指摘を閉じない。
- 要求の変更や重要なリスクの受容が必要なら、権限を持つ人へ判断を求める。
- 情報不足や環境不足は、調査・環境整備へつなぐ。確認不能を合格や不合格へ丸めない。
- 同じ争点で根拠が増えない場合は、レビューを無制限に繰り返さない。反証可能な確認を試し、なお解消できなければ争点と影響を明示して判断を求める。

レビューの結果には、何を確認し、何を確認できず、何が完了を妨げているかを残す。機械が進行判断に短い結果を使う場合も、単一のtrue/falseだけで原因・対象・根拠を失わないようにする。

### チームが判断するための見せ方

PRから、Issueの完了条件とその証拠、重要な指摘と対応、残る制約を辿れるようにする。詳細なログは参照先に置き、要点を読めばレビューや引き継ぎの判断ができる形にする。要求全文を別のチェックリストとして複製しない。

人への確認は、必要な判断・選択肢・影響・推奨案をまとめて提示する。進行状況の共有と承認依頼は区別する。マージ前の人のレビュー・承認を標準とする。合意済み資産による観点の限定と、事前合意した条件による人のレビュー省略を検討する方針へ更新する。具体的な省略条件は未決定のため、現段階では標準を適用する。LLMレビューの合格は、人の承認やマージ権限を自動的に付与しない。チームで誰が承認できるかは、権限設計で決める。

### PRの粒度と承認の対象

PRは人がレビューできる大きさとする。目的・影響・検証を一まとまりで判断できることを基準にし、一律の行数上限は現段階では設けない。無関係な整理を混ぜず、必要なコード・テスト・文書を合わせて提示する。

一つのIssueを複数のPRで実現してよい。各PRで何を実現し、何に依存し、何が残るかを示す。分割したPRのマージをIssue全体の完了とは扱わない。根本解決に必要な範囲を維持しながら、段階的な変更がそれぞれ安全に取り込める構成を検討する。

人の承認は評価した変更に対応させる。承認後に変更した場合、古い承認だけで新しい内容をマージ可能とは扱わない。どのGitHub設定でこの条件を強制するかは、利用可能な機能を確認したうえで設計する。ここでの文書化は設定済みの宣言ではない。

### 合意済み資産によるレビュー範囲の限定

| 合意済みの資産 | 合意と検証の範囲内で省ける確認 | 今回の利用で残る確認 |
| --- | --- | --- |
| ロジック・共通関数 | 未変更の内部処理について、適用条件内で確認済みの性質。 | 選択の適切さ、入力、呼び出し方、エラー処理、他の処理との接続。 |
| UIコンポーネント | 合意された状態・設定における見た目や振る舞い。 | 組み合わせ、表示内容、状態の選択、画面内の使い方。 |
| デザインシステム | 合意済みの色・余白・文字・部品の規則。 | 情報設計、操作の流れ、画面全体の使いやすさ、組み合わせによる問題。 |

今回利用した資産、対象版、合意の根拠、適用条件と保証範囲を参照できるようにする。資産の文書・コード・設定など既存の情報を使い、必ず専用の承認台帳を新設するとは定めない。単に共通部品をimportしていることでは、適切な利用や画面全体の品質を証明できない。

環境は合意済み資産と適用条件を備え、コンテキストは今回の利用と合意の関係を伝える。ガードレールは機械的に確認可能な変更・逸脱・利用条件を検出し、ハーネスは残る観点に必要な検証とレビューを実行する。これは今後実現する責任分担であり、既存ツールで全条件を判定できるとは仮定しない。

スクリーンショットや操作動画は、残る観点を人が確認する負担を減らす。対象の変更、重要な状態、操作の結果を示し、必要なら音声解説や字幕を添える。画像や動画があるだけでは、その観点を機械的に検証したことにはならない。

### 人のレビューを省略する経路の検討条件

まずレビュー観点を限定し、その後に残る観点を機械的に確認できるかを判断する。省略する対象は変更ごとの人のレビューであり、要求の合意・必要な検証・チームへの可視化は維持する。

省略条件は対象となる変更の種類・範囲・リスクと必要な検証を事前に合意し、チームから確認できるようにする。今回の変更がその条件に該当し、最終的な成果物に対する検証がすべて成功し、未検証事項や想定外の差分がないことを確かめる。条件の不一致や確認不能があれば人のレビューへ戻す。LLMがその場で例外を作ることは認めない。

Issue・PRには適用した条件と検証の証拠を残す。PRのレビュー可能な粒度も維持する。人のレビュー省略と、マージ操作の承認・自動マージは別の決定とし、具体的な承認・実行権限が決まるまでは自動化しない。

具体的な資産と利用例で、誤った使い方や条件逸脱が検出できるかを評価する。レビュー観点の限定を、品質基準の緩和として扱わない。

### 利用例による確認範囲の具体化

以下は仮想の製品を使った机上検討であり、このリポジトリに該当する資産・検証が存在するという意味ではない。省略経路を有効にする決定でもない。

| 利用例 | 再確認を省ける範囲 | 今回必要な証拠・評価 | 人のレビューの扱い |
| --- | --- | --- | --- |
| 合意済みの日付整形関数を一覧へ適用する | 指定した入力形式・タイムゾーン・欠損値の条件における未変更の整形処理。 | 実際のデータとの接続、利用するタイムゾーン、欠損時の表示、対象画面以外への影響を確認する。境界をまたぐ日時などで期待する表示を検証する。 | 接続や表示仕様まで事前合意され、逸脱を機械的に検出できれば省略候補。共通関数の利用だけでは省略しない。 |
| 合意済みの検索部品を別の一覧画面へ追加する | 承認された設定内での部品単体の描画・操作。 | 検索対象、絞り込み結果、空・エラー・読込中の状態、画面のフォーカスや操作のつながりを検証する。重要な状態の画面・動画を添える。 | 部品内部の確認は絞れるが、画面内の配置や検索の使い勝手に新しい判断が残るため、その観点は人が確認する。 |
| デザインシステムで新しい画面を組み立てる | 既定の部品やトークンについて合意済みの性質。 | 情報の優先順位、組み合わせ、長い内容や狭い画面での表示、操作の流れを確認する。 | 構成自体が新しければ人の判断が残る。トークン準拠やスクリーンショット生成だけでは省略候補にしない。 |
| 合意済みの画面テンプレートへ、指定された表示項目を追加する | テンプレートと許可された組み合わせの確認済みの性質。 | 項目・順序・表示内容がIssueの合意と一致し、許可外のコード変更がないことを確認する。対象状態の動作と表示を検証する。 | 変更が許可された設定に閉じ、残る条件をすべて機械的に確認できる場合に、最初の限定的な省略候補とする。 |

部品への合意と、部品を組み合わせた利用パターンへの合意は区別する。既存資産を使いながら自由なコードを追加する変更は、その追加部分の評価が残る。一方、合意済みの利用パターンの範囲で完結する変更は、確認範囲をより限定できる。このためだけに汎用DSLや画面生成基盤を新設することは提案しない。

### 限定した省略候補を評価する方法

最初の候補は、既存の合意済みテンプレートや設定で表現できる変更とする案が有力である。対象となる実際の資産はまだ選定していない。導入時には対象のプロジェクトから選び、次を確かめてから人に採否を判断してもらう。

- 正しい利用例で、要求に対応する検証が成功する。
- 許可外の入力・設定・組み合わせ、部品の直接変更、独自の回避処理を加えた例が、省略条件を通過しない。
- 検証の削除・弱体化や、表示比較の基準画像の更新によって、誤実装がそのまま受け入れられない。省略条件や検証基準の変更自体は、同じ省略経路で承認しない。
- 要求・依存資産・検証対象が変わった場合や、証拠が欠けた場合に、人のレビューへ戻る。
- 当初は人のレビューも併用し、見落とし、誤った差し戻し、人の確認時間、検証・仕組みの維持費を記録する。省略を模擬した判断と、人の評価の違いを比較する。

確認結果はこの変更の種類と条件に限定して解釈する。合格例だけから、別のコンポーネントや新しい画面にも省略可能と一般化しない。

PRでは、再利用した合意、今回新たに確認する点、その証拠を短く示す。新しい必須書式を増やす前に、通常の変更説明へ組み込む。例えば検索部品の追加なら「部品単体の既定動作は既存の合意を参照し、今回は検索対象・結果・画面内の操作を確認した」と読める形にする。
