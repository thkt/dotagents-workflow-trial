# OUTCOME 改訂案

チーム開発で達成したい状態をまとめたレビュー用草案。現在の運用は[DEVELOPMENT.md](../../DEVELOPMENT.md)を参照する。この草案の保存だけで運用規則を変更しない。

## 目的

チーム開発を前提とし、要求・合意・進行状況・成果・判断の根拠を共有することで、担当者や利用するエージェントが変わっても、他のメンバーが確認・レビュー・引き継ぎできる状態を保つ。

相談や課題を起点に、根拠と選択肢を整理し、実現すべき要求・品質基準・完了条件を明確にして合意する。

必要な成果物を作成し、要求の達成と成果物の品質を検証・レビューしたうえで、判断と達成の根拠とともに届ける。実装しないという判断も、根拠に基づいて合意された場合は成果とする。

得られた有効な知見を次の判断と開発に反映し、品質を維持しながら、不要な人の介入とチーム全体の運用負担を減らす。

## 達成した状態

| 観点 | 達成条件 |
| --- | --- |
| 要求の明確化と合意 | 元の目的、要求、対象外、品質基準、完了条件が明確で、重要な不確実性とトレードオフについて必要な合意がある。 |
| 要求の達成 | 合意内容と成果物が対応し、未達事項が明示されている。利用後に確認する効果は、成果物の完成と区別されている。 |
| 品質の確認 | 成果物に応じてコード・テスト・ドキュメントが検証・レビューされ、完了を妨げる指摘が解消されている。残る制約と未検証事項が明示されている。 |
| 根拠と作業状態の追跡 | 判断・検証の根拠が対象の成果物と対応し、失敗や未検証が成功扱いされない。中断時にも状態を把握できる。 |
| 作業範囲の制御 | 合意した権限と変更範囲を守り、必要な再合意を経て、安全に継続または終了できる。 |
| 知見の再利用 | 有効な知見が適切なコード・テスト・ドキュメントに反映され、次の関連作業で参照・更新できる。 |
| チームでの状態共有 | 作業の目的、担当、進行状況、判断待ちの事項を他のメンバーが確認できる。 |
| チームでのレビューと意思決定 | 元の会話に参加していないメンバーも、要求・変更・根拠を理解して判断できる。変更は人がレビューできる単位で提示され、合意済みの品質と今回確認すべき品質を区別できる。合意したレビュー・承認条件を満たしてからマージされる。 |
| 引き継ぎ | 個人の会話履歴や記憶だけに依存せず、必要な情報から別の担当者が作業を継続できる。 |
| 並行作業 | 他のメンバーの変更や判断を把握し、衝突や要求の食い違いを調整できる。 |
| 運用効率 | 共通の品質基準のもとで、人の介入、手戻り、時間・コスト、仕組みの保守負担に加え、チーム全体の説明・確認・レビュー・引き継ぎ・調整の負担を測定し、改善を評価できる。 |

品質の維持は、同じコードの生成ではなく、共通の品質基準で評価し、逸脱を検出・修正できることを指す。検証・レビューによって、すべての不具合が存在しないと保証するものではない。

減らす対象は不要な確認や進行管理であり、目的や優先順位を決める有意義な対話は含めない。

## 文書の役割

- この文書は目的と達成状態を定める。
- [開発方針案](development-policy-draft.md)は、継続的な判断の原則を定める。
- [概念と責任範囲](architecture-concepts.md)は、共通語彙と責任の境界を定める。
- 今後の設計計画は、具体的な責任の配置、採用する仕組み、評価方法、移行手順を定める。

工程の区分・名称・構成、解析ツール、データ形式、状態管理方式は設計で検討する。工程は目的の達成に必要な責任と判断から選ぶ。
