# アーキテクチャの概念と責任範囲

[OUTCOME 改訂案](OUTCOME-draft.md)と[開発方針案](development-policy-draft.md)を補助する、会話で合意した共通語彙。この文書を4つの概念の定義の正本とする。現行実装がこれらの責任を満たしていると宣言するものではない。

## 定義と境界

| 概念 | 定義・担う責任 | 保証の境界 |
| --- | --- | --- |
| ハーネス | 作業の進行と状態を管理する仕組み。工程の実行、結果の受け渡し、修正への差し戻し、停止・再開を担う。 | 進行を管理するだけでは、要求・実装・レビューの判断の正しさは保証しない。 |
| ガードレール | 作業や完了判断で守る境界を強制する仕組み。権限・変更範囲の制限、必須検証、未達・未検証での完了防止を担う。 | 強制できるのは、定義され、観測・判定できる境界。文書の指示やLLMへの期待だけでは、強制されたことにならない。 |
| 環境 | 作業に利用できる道具・資産・実行条件。コード、共通部品、テスト、解析ツール、ドキュメント、実行環境を備える。 | 利用可能であることと、適切に選択・使用されることは別。 |
| コンテキスト | その時点の判断に実際に使う情報。目的、合意した要求、関連コード、設計理由、証拠、失敗や指摘を選び、届ける。 | 渡しただけで理解・遵守されたとは限らない。必要な情報の欠落、古さ、矛盾も判断に影響する。 |

これは責任の分類であり、4つのモジュール、ディレクトリ、エージェントを作る要求ではない。同じ仕組みや資産が複数の役割に関わる場合もある。具体的な配置や実装方式は設計計画で決める。

## 合意済み資産との関係

4つの概念は「何を担うか」という責任の分類である。合意済み資産は「何が、どの範囲で合意され、再利用できるか」という別の軸として扱う。第5の実行機構を追加するものではない。

このプロジェクトでは、合意済み資産を、チームが利用を合意した具体的な実装・設定・定義・情報と、その適用条件・品質基準・検証方法・判断根拠として捉える。対象はロジックやUI部品に限定しない。

| 担う責任 | 合意済み資産になり得るもの |
| --- | --- |
| ハーネス | 作業の進行、差し戻し、再開の仕組みと利用条件。 |
| ガードレール | 必須検証、権限、完了・マージ条件の規則と設定。 |
| 環境 | 開発環境の定義、共通ロジック、コンポーネント、デザインシステム。 |
| コンテキスト | 判断に渡す情報の構成、共有する用語の定義、適用対象が明確な合意済み要求。 |

4つに分類されるだけで合意済みになるわけではない。特にコンテキストには未合意の提案・仮説・未検証情報も含まれ、情報の構成への合意を、その中身すべてへの合意と混同しない。

合意した対象版・範囲・適用条件を確認して、要求定義から実装・検証・レビューまで再利用する。合意は動作の正しさや無欠陥を自動的に保証しない。仕組みや規則の変更も、影響する合意と証拠を再評価する。記録と運用は[開発方針](development-policy-draft.md)と[情報・合意・証拠の設計案](information-and-evidence-design.md)で扱う。

## 連携の例

### 開発方針と解析ツール

開発方針のドキュメントや解析ツールが利用できる状態は、環境の一部である。関連する方針や解析結果を実装者・レビュアーが参照すると、コンテキストになる。

ハーネスが必要な工程で解析を実行し、指摘を修正工程へ渡す。必須の解析が失敗・未実行なら完了できないという制御は、ガードレールに当たる。ツールを導入しただけ、実行を指示しただけでは、この制御があるとは扱わない。

### LLMレビューと完了判定

レビューに必要な要求・品質基準・対象コード・検証結果をコンテキストとして提供する。ハーネスがレビューを実行し、指摘の評価と修正へつなぐ。完了を妨げる指摘が未解決なら完了を許可しない制御は、ガードレールに当たる。

レビューを通過しなければ完了できないことと、レビューがすべての問題を正しく検出することは別である。指摘の妥当性とレビューの検出力は、開発方針に沿って評価する。

## 問題の切り分け

| 観測した状態 | 調べる責任の例 |
| --- | --- |
| 必要な共通部品や検証手段が存在しない | 環境：適切な資産・能力が備わっているか。 |
| 適切な共通部品は存在するが、実装時に参照されない | コンテキスト：関連情報が選ばれ、判断に届いているか。 |
| 必須テストが失敗しているのに完了になる | ガードレール：失敗が完了を阻止するか。 |
| 失敗は記録されるが、修正や停止判断へ進まない | ハーネス：結果に応じた進行が行われるか。 |

この表は調査の入口であり、観測だけで原因を断定するものではない。複数の責任にまたがる問題もある。例えば古い検証結果で完了した場合は、コンテキストの鮮度と、対象成果物への証拠の対応を確認するガードレールの両方を調べる。

## 工程との関係

工程は4つの概念とは別の軸である。各工程で必要な環境とコンテキストを使い、ガードレールのもとで、ハーネスが進行を管理する。

目的の理解、判断材料の収集、要求と解決方針の合意、記録、実現、評価、成果の説明と知見の反映という仕事から、必要な境界を検討する。この列挙自体も固定の工程数や実行順序を定めるものではない。

必要な情報・権限・独立性・再開単位が変わるか、分離によって品質や運用効率が改善するかを基準にする。工程、役割、成果物、ツールを混同せず、統合できる仕事と独立した確認が必要な仕事を見極めてから名前を付ける。

工程の連携、必要な工程の選択、問題に応じた差し戻し先は、今後の設計計画で具体化する。すべての不合格を実装修正へ戻すと、事実不足や要求の矛盾を解消できないため、原因に応じた対応を検討する。

## 設計前提：GitHubを必須の環境とする

当面の開発環境としてGitHubを必須とする。要求と合意の記録、コード変更の共有、レビュー、検証結果の確認に活用する。サービスの提供条件や開発上の必要性が変わった場合は、この前提を見直す。

GitHub Actionsを、CI/CDによる検証・確認環境の提供、ドキュメント整備のフック、環境の整備・維持を実行する基盤としても位置づける。具体的な配置案は[実行構成の検討記録](archive/execution-design.md)に記載する。Actionsによる起動・実行はハーネス、そこで使う資産は環境、結果による進行制限はガードレール、次の判断に渡す結果はコンテキストとして扱う。

これは合意した設計前提であり、現行環境の設定済み機能や有効性を示すものではない。具体的な機能、権限、設定は設計・導入時に確認する。

変更の大小を問わずIssueを必須とし、要求の正本およびチームが目的・合意・進行状況・結果を確認する入口とする。合意範囲に対応する既存Issueは再利用する。この方針は決定事項とし、具体的な記録・更新手順は設計で定める。

以下のうちIssueの役割は決定事項であり、その他は配置の候補である。

候補を具体化する検討内容は[情報・合意・証拠の設計案](information-and-evidence-design.md)に記載する。実装や運用への採用は別途行う。

| 対象 | 役割の候補 |
| --- | --- |
| Issue | 要求・完了条件・合意内容の正本。 |
| Pull Request | 変更の説明、レビュー、対応状況。 |
| リポジトリ内の文書 | 開発方針、設計理由、再利用する知見。 |
| CIの実行結果 | 対象の成果物に対応する自動検証の証拠。 |
| マージの制御 | 必要な検証・承認を満たさない変更を止めるガードレール。 |

GitHubを必須にすることと、Issue作成を独立した工程にすることは別である。IssueやPull Requestが存在するだけで、合意済み・検証済みとは扱わない。何を根拠にその状態と判断するかを設計で定める。

将来のサービス切り替えのためだけの汎用機構は、現段階では設けない。まずGitHubを前提に具体化し、前提を見直す際にも要求と判断理由を読み取れる形で残す。

## 設計と説明での使い方

各仕組みについて、どの責任を担うか、何を根拠に判断するか、何が実際に強制されるかを説明する。意図している動作、実装済みの動作、検証で確認できた動作を区別する。

目的と達成状態はOUTCOME、継続的な判断原則は開発方針、用語と責任の境界はこの文書、具体的な構成・評価・移行は設計計画で扱う。定義をほかの文書へ複製せず、この文書を参照する。
