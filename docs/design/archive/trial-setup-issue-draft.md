> 保存された設計・試行記録です。本文の進捗・提案・実行上限は記録当時のものです。現在の操作や権限には適用せず、[設計の入口](../README.md)から現行手順を確認してください。

チームがIssueで要求を共有し、Appが作成した小さなPRを、CIの結果と根拠を見て人が承認できる試行環境を整える。対象はこのPublicリポジトリと架空データのみ。

## 範囲と進め方

- 初期化：空リポジトリの最初のmain作成は、通常のPR運用を始めるための一度限りの準備として別に扱う。最小READMEの内容と直接作成の扱いを実行前に明示する。
- 共通の検証：ローカルとActionsが同じ検証コマンドを使う。Oxlintと、BiomeのnoExcessiveCognitiveComplexityだけを採用する。具体的な設定・バージョン・閾値は設定PRで説明する。
- CI：PRの対象commitを検証する。必須検証が失敗・欠落・スキップした状態を成功扱いしない。秘密鍵や書き込みtokenを持つ処理でPRのコードを実行しない。初期案は1実行10分上限・同一PRの古い実行をキャンセルする構成。
- マージ保護：人の承認1件と必須CIを要求し、新しい差分では承認を見直す。Appにbypassを付与しない。必要なチェックが実際に発行されることを確認してから保護を有効化する。
- 主体分離：AppがPRを作成し、thkt本人がレビュー・承認する。エージェントがthktの認証で承認を代行しない。初期workflow・保護設定の変更権限はAppの権限と区別する。
- 文書：セットアップ、検証、公開操作、確認済み範囲、未確認事項を記録する。現行ハーネス一式はコピーしない。

## 完了条件

- [ ] 新しいcheckoutから文書に沿って検証でき、Actionsでも同じ検証が動く。
- [ ] App作成の確認PRがこのIssueを参照し、人が読める差分と検証根拠を持つ。
- [ ] 必須CIの失敗・欠落・未承認時にはマージ可能と扱われないことを実際の状態で確認する。
- [ ] 検証・承認後に差分を変えた場合、古い結果だけでは完了と扱われない。
- [ ] thkt本人によるレビュー・承認を確認する。自動マージは行わない。
- [ ] 設定値、対象commit、CI run、PR、確認者を対応づけ、未検証を明記する。
