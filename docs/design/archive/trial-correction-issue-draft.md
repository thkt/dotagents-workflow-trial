## 完了条件

1. 必須checkを実行して終了結果を取得する。失敗時はログ・対象・未達条件を修正担当へ渡し、成功やレビュー準備完了を報告しない。
2. check成功後、独立した評価実行が要求と成果物・証拠を直接確認する。未達なら具体的な指摘を修正担当へ渡す。応答欠落・解釈不能・実行失敗は受け入れとみなさない。
3. 修正後の対象でcheckと必要な独立評価をやり直す。要求または成果物が評価中に変わった場合は、その結果を新対象の成功証拠に流用しない。対象の対応には文書の変更も含む。
4. 修正・評価の開始前に残り回数と累計実行時間を確認する。上限到達時には次のモデルを開始せず、実行中の時間超過も終了を確認して未達を記録する。同じ試行の再実行で回数を初期化しない。
5. 要求変更・追加権限・実行上限の引き上げが必要な場合は、根拠と必要な判断を残して停止する。通常の修正判断はLLMに任せ、工程の中継だけのために人を呼ばない。
6. 全条件が揃った状態は「人のレビューに渡せる」とする。自動マージや成果の受け入れとは区別する。試行実行の中からGitHubへ書き込まず、既存の公開担当が証拠を確認してPRを作成する。

## 検証ケース

| ケース | 期待する結果 |
| --- | --- |
| check失敗→修正→成功 | 失敗根拠を渡し、修正後のcheckと独立評価を実行する。 |
| check成功・文書監査は未達 | check成功だけで通過せず、文書修正と再評価へ戻る。 |
| 評価中に対象が変化 | 古い受け入れ結果を採用しない。新対象の確認が必要だと記録する。 |
| 評価応答が欠落・不正、または処理失敗 | 成功扱いしない。原因を記録し、無制限に再試行しない。 |
| 回数または時間の上限に到達 | 次のモデルを開始せず、時間超過した実行の終了を確認し、未達と消費量を残す。 |
| 同じ試行を再実行 | 消費済み回数を保持し、同名の証拠を上書きしない。 |
| 全条件が成功 | 対象に対応する証拠を添えてレビュー準備完了を示し、マージしない。 |

まず同じ実行入口に制御可能な検証・モデル応答を与え、上の分岐をモデルなしで確認する。試験専用の別制御経路を作らない。これは手続きの検証であり、LLMの修正能力を確認した結果には数えない。

実モデル試行は、隔離した作業コピーへ検索の大小文字処理の不具合とREADMEの古い記述を意図的に与え、通常の要求と実際の失敗・指摘から復帰させる。正解の差分は修正担当へ渡さない。修正担当が両方を先に直す可能性があるため、文書監査からの差し戻しが必ず発生したと扱わず、実際に通過した経路を記録する。

## 合意済み実行上限

追加の実モデル試行はすべてAstra/high、修正最大2回・独立評価最大2回、モデル実行の累計20分とする。上限に達したら残る問題を報告し、暗黙に追加しない。初回の実行量とは別に集計する。料金の上限ではなく、モデルなしの検証・準備・CI待ち時間もこの20分には含めない。

この上限は試行する接続の動作を測るためのもの。接続自体の実装やレビューを別モデルへ委譲する場合、その実行も事前に別途上限を合意する。現在の担当による実装・確認と混同しない。

## 必要十分な実装と対象外

既存の実行環境で分岐と証拠対応を強制できるか先に確認し、不足する接続だけを実装する。評価結果の読み取りと対象対応に必要な最小データは持つが、要求を独自の巨大な契約へ翻訳しない。CLI・SDKの選択は必要な制御から決め、旧ハーネスをコピーしない。

要求変更の自動承認、レビュー省略、自動マージ、公開操作の再送、並行実行、プロセス障害からの完全自動再開、改変不能な外部判定基盤は対象外。同じ作業コピーへの並行実行を前提にしない。途中状態が不明なら続行せず照合する。

PRには変更理由、制御の小さな図、ケース別結果、実際のモデル呼び出しと対象、消費量、人の介入、未確認を記載する。公開用には要約と再現方法を残し、秘密値を含むログを公開しない。コードの完了条件・有用なテスト・冗長さは独立したレビュー観点とし、模擬応答で分岐が通ることだけで十分と判断しない。
