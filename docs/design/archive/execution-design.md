# 最小の実行構成案

> 保存された設計・試行記録です。本文の進捗・提案・実行上限は記録当時のものです。現在の操作や権限には適用せず、[設計の入口](../README.md)から現行手順を確認してください。

[OUTCOME](../OUTCOME-draft.md)、[開発方針](../development-policy-draft.md)、[概念と責任範囲](../architecture-concepts.md)、[情報・合意・証拠の設計案](../information-and-evidence-design.md)から導く構成。現行の工程、SDK、保存形式を前提にしない。2026-09-10に初回試行の結果を反映した。以下の配置方針と、実際に強制・実測できた範囲は区別する。

## 初回試行後の自動化と判断の配置

「実行上限」は、自動で作業を続けてよい回数・時間、および必要に応じて合意する利用料金の上限を指す。納期・開発費などの事業上の制約とは区別する。初回試行で合意したのは回数・時間の上限であり、料金の上限ではない。

[Issue #10の完了記録](https://github.com/thkt/dotagents-workflow-trial/issues/10#issuecomment-5604167240)と[評価結果](https://github.com/thkt/dotagents-workflow-trial/blob/5cff1d6f0ae8ad839e23c05965f8128a72998429/evidence/issue-10/evaluation.md)を根拠とする。初回は親タスクが進行・公開を担当した。個々の検証成功を、進行制御全体の自動化完了とは扱わない。

| 仕事 | 配置する責任 | 現在の証拠と不足 |
| --- | --- | --- |
| 要求の精緻化・資産の適用判断 | LLMが調査・選択肢・完了条件を具体化し、人が目的・範囲・重要なトレードオフを合意する。 | Issueで要求を共有した。要求変更時の再合意・証拠更新は未試行。 |
| 合意範囲の実装・文書更新 | LLMが必要な作業を選び、通常の修正は都度人に許可を求めず進める。 | 商品一覧・検索とREADMEを実装した。工程別の固定エージェント列は不要。 |
| 静的・動作検証 | 機械が共通checkを実行し、終了結果を取得する。 | Oxlint、Biomeの複雑度上限15、Playwright E2Eをローカル・CIで実行。不具合注入でE2Eの失敗を確認した。 |
| 要求達成・コード・テスト・文書の評価 | 作業担当とは別のLLM実行が要求・成果物・証拠を直接確認する。 | 動作テストでは検出しない文書不足を検出し、修正後に再評価した1例。見逃し率は未評価。 |
| 失敗から修正への復帰 | 機械が失敗・対象・証拠を渡し、LLMが原因と修正方針を判断する。合意した実行上限内で再検証する。 | 文書修正への接続は親タスクが担当。不具合注入の復元も親タスクであり、自動復帰の実証ではない。 |
| PRの説明・証拠の準備 | LLMが説明を選び、道具が撮影・添付・公開を行う。 | 画像比較表、Playwright動画、macOS音声、Mermaid図を共有した。これらの作成全体を自動化したわけではない。 |
| マージ前の確認 | 機械が必須CIと最新承認を確認し、人が残るレビュー観点と検証定義の変更を判断する。 | 最新headの承認、CI、マージ、main CIを確認。現在は人がマージを実行する。 |
| 中断・公開結果不明・他者の変更 | まず現在の対象と外部結果を照合する。解決に要求・権限・実行上限の変更が必要なら人へ戻す。 | この経路の耐久性、重複防止、並行作業は未試行。 |

人を呼ぶ条件は、目的・範囲・受け入れ条件の変更、未合意の重要なトレードオフ、追加権限の必要・実行上限の引き上げ、最終レビュー・承認である。情報不足はまず調査し、検証失敗はまず合意範囲内で修正する。上限到達・確認不能の場合は未達と根拠を残し、人の判断が必要な内容を具体化する。LLMが要求や検証基準を弱めて成功へ進めてはならない。

機械が確認できるのは実行結果や対象の対応などの手続きであり、意味的な正しさ全体ではない。検証定義もPRから変更できる現構成では、その変更を人が見落として承認した場合まで防げない。人のレビュー省略・自動マージ・PRから独立した強制判定は今回の採用範囲に含めない。

## 責任の配置

| 責任 | 配置案 | 分ける理由 |
| --- | --- | --- |
| 仕事を進める | 作業を担当するLLMが、必要な調査・対話・設計・実装・自己確認・説明を行う。 | 情報不足や失敗の原因に応じて行動を選べるようにする。工程ごとの別担当を最初から必須にしない。 |
| 独立して評価する | 作業担当の自己確認とは別の評価機会を設け、要求・対象成果物・証拠を直接確認する。 | 実装担当の完了宣言や説明だけで受け入れない。対象の重要性に応じて、要求の評価にも使う。 |
| 実行と進行を制御する | 必要な検証・評価を実行し、結果を修正へ渡す。権限・対象・証拠を確認して、完了や外部操作への進行を制御する。 | 作業担当やレビュアーの指示だけで必須確認が飛ばされないようにする。ハーネスとガードレールの責任をここへ配置する。 |

これは3エージェント、3サービス、3固定工程の指定ではない。作業担当と評価担当にはLLMを利用する案とし、実行制御のためだけに追加の判断エージェントを置くことは初期案では求めない。静的検証・テストは道具として実行する。既存の実行環境で強制できる条件はそこで扱い、不足する制御だけを追加する。

評価は毎回すべての観点を一からやり直すものではない。合意済み資産で確認済みの範囲を除き、今回の要求と変更で残る観点に集中する。評価の独立性・省略条件の詳細は情報設計を参照する。

## 作業が進む仕組み

作業担当は、現在の合意と不足している情報・証拠から次の行動を選ぶ。調査報告や設計書を工程通過のためだけに作成せず、判断と引き継ぎに必要な情報を残す。変更作業はIssueに紐づけ、合意範囲内で進める。

必須検証や評価の失敗は、原因・対象・証拠とともに作業担当へ戻す。進行を制御する側は、失敗を記録するだけでなく、修正・追加調査・必要な人の判断・停止のいずれにつながったかを把握する。次の行動が意味的に適切かはLLM等による判断を伴い、その正しさを手続きの強制と混同しない。

条件が揃ったら、レビュー可能なPRと説明を準備する。PRの作成は、成果の受け入れやマージとは別の操作として扱う。途中経過を共有するPRが必要な場合も、未検証・未完了を明示する。外部操作は既存の許可範囲で行う。

マージ前には対象に対応する検証・評価と人の承認を確認する。将来、事前合意した人のレビュー省略条件を導入しても、適用条件の確認と証拠は省かない。現在は具体的な省略条件が未確定のため、人のレビュー・承認を標準とする。

## 機械的に守る境界の候補

- 合意した対象と権限に対応する作業だけを許可する。意味的な範囲逸脱はレビューでも確認する。
- 必須検証を実行し、実際の結果を取得する。LLMの「成功した」という説明で代用しない。
- 評価した要求・成果物・条件と、完了またはマージする対象の対応を確認する。
- 未解決の必須条件、失敗、確認不能があれば、成功として進めない。
- 人の承認または将来の合意済み省略条件を確認する。作業担当が自分で基準を緩めて通過できないようにする。
- 中断後は現在のコード・Issue・外部操作結果を照合する。応答不明の公開操作を無条件に再実行しない。

これらの境界をどう強制するかは次の技術検討で確かめる。GitHubの設定、実行環境の権限、必要な小さな制御コードなどを比較し、宣言だけでは満たしたとしない。

## 最小限残す実行情報

GitHubは共有・マージ制御に加え、GitHub Actionsによる検証、ドキュメント整備、環境の整備・維持の実行基盤として使う。具体的な配置は次節の案に従って検討する。

再開と完了判断に必要なのは、対象Issueと合意内容の識別、作業中の変更、実行した検証・評価とその対象、未解決事項、外部操作の確認済み結果である。GitHubを共有情報の入口とし、作業環境には公開不要の実行・再開情報を残す。

要求全文や履歴を複数の編集可能な正本にしない。対象の同一性を確認するための記録と、人が更新する正本は区別する。永続化の方式、排他の範囲、再実行の識別方法は、実際に起こりうる中断・並行作業のケースに必要な範囲から選ぶ。

## GitHub Actionsによる品質・文書・環境の維持

変更を作る仕事と、成果物・開発環境を維持する仕事を接続する。以下は役割と起動契機の設計案であり、workflowの作成や外部環境の構築はまだ行わない。役割ごとに別workflowを必須にしない。

| 役割 | 起動契機の候補 | 実行する仕事と残す結果 |
| --- | --- | --- |
| CIでの検証 | PR作成・更新、必要な再検証 | 共通の環境で静的解析・テスト・ビルドを実行する。対象の要求・変更・環境と結果を辿れるようにし、必須検証の未実行を成功扱いしない。 |
| プレビューと操作確認 | 画面など、実際の利用状態の確認が必要な変更 | 適切な配置先へ対象の版をデプロイし、E2E・画面・操作動画などの証拠を用意する。PRからURL、対象版、利用期限が分かるようにする。 |
| 文書の整備フック | 関連コード・仕様・文書の変更 | 生成文書の差分、リンクやコードとの整合性、更新が必要な記述を確認する。必要に応じて更新候補を作り、通常の変更・レビューへ戻す。 |
| 環境の整備・維持 | 環境定義・依存関係の変更、必要な定期確認 | 新しい環境からのセットアップと必須検証を確認する。更新が必要ならIssueへ紐づく変更案を提示する。 |
| 合意された成果の配布 | マージ・リリースなど、許可した契機 | 承認済みの対象を配布し、結果を記録する。マージと本番リリースの許可を同一視しない。 |

GitHub Actionsは起動・実行を担う。プレビューの実際のホスティング先や必要な外部資源は別途選び、GitHubのEnvironmentを作るだけでアプリの実行基盤も用意されるとは扱わない。プレビューは不要になった際に片づけられるよう、所有者・対象・削除条件を決める。

### ドキュメント更新の扱い

コードから機械的に導けるリファレンス等は生成し、元のコードと生成物の対応・差分を確認する。設計理由・適用条件・推奨する使い方は、根拠から更新候補を作り、意味的なレビューを受ける。自動生成やLLMの要約によって、資産の合意状態や品質基準を新しく確定しない。

要求達成に必要な文書は、可能な限り元のIssue・PRに含める。生成結果はまず差分として提示し、自動でbranchを書き換えることを初期案の必須にはしない。変更を適用したら対象が変わるため、必要な検証・レビューを更新する。自動更新で古い成功結果や人の承認を使い回さない。

独立した保守変更は別Issue・PRへ紐づける。元の成果を完了とするために必要な文書を、マージ後の任意の整備へ先送りしない。同じ差分の再提案や生成・再起動の循環を避ける。生成結果が変わらない実行では変更や通知を増やさない。

### ローカルと共有環境の分担

ローカルでは原因調査と素早い修正確認、共有環境では再現可能な必須検証とチーム向けの証拠取得を行う。同じ検証定義を利用し、ローカル専用・CI専用の重複した品質基準を作らない。差が必要な場合は実行条件と理由を明示する。

キャッシュのない新しい環境からもセットアップできるかを確認する。実行環境の版や依存関係を記録し、キャッシュ成功だけで再現性を判断しない。すべてのPRで全環境を再構築するかは費用とリスクから決める。

### 自動処理と変更権限の境界

PRのコードを実行する検証と、リポジトリへの書き込み・配布権限を持つ処理を分ける。検証対象が自身の成功証拠や省略条件を自由に作れる構成にしない。外部由来のコードや成果物を扱う場合も同じ境界を守る。

Actionsが生成した変更についても、必要な検証が再実行されたことを確認する。イベントの再起動はトークンやイベント種類の仕様に依存するため、pushすれば必ず次のworkflowが走るとは仮定しない。対象版と実行結果を確認してから進める。

### この配置を検証するケース

- 文書の更新漏れを検出し、生成差分の適用後に検証対象が更新される。
- 生成処理の再実行で同じIssue・PR・通知を増やさない。
- プレビューで確認した版とマージ候補が一致し、古い画像・動画が最新の証拠として扱われない。
- 新しい環境でセットアップでき、失敗を環境要因とコード要因に切り分けられる。
- スキップされた必須検証、生成基準の変更、権限のない公開が成功経路へ進まない。

これらは今後の検証計画であり、動作確認済みではない。

## 初期案で固定しないこと

- 調査・設計・実装ごとのエージェント数や、毎回必ず通る工程列。
- 常時稼働する管理エージェント、多段のレビュー、独自の巨大な状態管理層。
- SDKの採用・不採用、特定の実行ホスト、機械向けデータ形式。
- 人のレビュー省略条件、自動マージ、チームの具体的な承認者。

SDK等は、必要な制御と証拠取得を実現できるか、既存機能との重複や保守負担がどうかで選ぶ。採用自体を目的にしない。

## 構成を評価する条件

同じ要求・モデル条件・品質基準で、要求達成、見落とし、不要な停止、人の介入、レビュー時間、実行時間・コスト、保守負担を比較する。通常の成功だけでなく、検証失敗、誤ったレビュー、要求変更、中断、外部操作の応答不明、他者の変更を含める。

作業担当が完了を宣言しても、検証失敗や古い証拠で完了できないことを確かめる。同時に、不要な工程や確認の繰り返しを増やしていないかを測る。机上検討と実測を分け、まだ試していない条件の保証を主張しない。

能力の読み取り調査は[実行環境とGitHubの能力調査](capability-assessment.md)に記載した。既存機能・現在の設定・追加が必要な制御・未実測を区別し、具体的な検証計画と選択肢を固めてから、実装へ移る判断を行う。

段階ごとの成果・完了条件・比較・移行は[実現・評価・移行の計画案](delivery-plan.md)を参照する。
