# 現在の開発手順を迷わず確認できる文書へ整理する

> 保存された設計・試行記録です。本文の進捗・提案・実行上限は記録当時のものです。現在の操作や権限には適用せず、[設計の入口](../README.md)から現行手順を確認してください。

## 目的

現在の検証・実行方法をREADMEから辿れ、同じ方針を複数箇所で更新せずに保守できるようにする。この実変更を現行TypeScript版の修正・独立評価フローで実施し、不要な処理や契約を実運用から見つける。

## 現在の問題

- READMEに「TypeScriptの型検証はありません」と残り、package.jsonのtypecheckと一致しない。
- READMEのcheck説明が現在の書式・型検査・制御テストを網羅していない。
- DEVELOPMENT.mdにIssueごとの追加記録が積み重なり、現在の規則と当時の状態を区別しづらい。

## 完了条件

- READMEから現在のセットアップ、共通check、商品アプリJSと制御TSの検証範囲を正しく確認できる。
- 現在の方針は適切な一箇所を正本とし、他の文書は必要な説明とリンクに絞る。新たな同期機構を追加しない。
- 人のレビュー・承認、検証変更の説明、画面変更の証拠、実行上限と中断の制約を失わない。
- 過去の実測結果と未検証範囲へ辿れる。過去の成功を現行版での実測として書き換えない。
- 初めて読む人が、通常の開発と制御CLIの試行を区別できる。
- コード・テスト・依存関係・CI・検証設定の変更は行わない。

## 検証と説明

既存のbun run checkを再利用する。独立したLLM評価は文書をpackage.json・設定・実行入口と照合し、完了条件、リンク、重複、保証の過大表現を確認する。文言一致だけのテストは追加しない。PRでは読む順序、統合した説明、保持した過去の記録を示す。

## 試行手順と評価

1. 合意したIssueを公開し、mainから隔離した作業コピーを用意する。
2. 現在の制御CLIでcheckと独立評価を実行する。既存checkが成功しても要求未達なら評価者がneeds_changesとして修正へ戻す。意図的な障害は追加しない。
3. 修正・再検証・再評価まで親タスクの中継なしで進むかを記録する。
4. PR作成とCI確認は公開担当が行い、人がレビュー・承認する。
5. 準備、実行、公開それぞれの所要時間、モデル呼び出し数、介入と理由、見逃し、不要だった入力・記録・処理を記録する。標準機能への置き換え候補は別の変更候補として整理する。

実行上限の提案：Astra/high、修正2回・独立評価3回・モデル実行累計20分。最初の評価を含むため独立評価を3回とする。上限で停止したら記録を保持し、無断で再実行・上限変更しない。この草案の作成時点ではIssue公開とモデル試行は未実施。

文書整理の1件による観測であり、画面実装・コード変更やハーネスなし構成との優劣まで一般化しない。
