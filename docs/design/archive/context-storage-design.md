# 調査・要求整理の実行手段とコンテキストの保存案

> 保存された設計・試行記録です。本文の進捗・提案・実行上限は記録当時のものです。現在の操作や権限には適用せず、[設計の入口](../README.md)から現行手順を確認してください。

[試行計画](discovery-trial-plan.md)に対応する設計案。スキル・保存・評価CLIの初期実装は[PR #52](https://github.com/thkt/dotagents-workflow-trial/pull/52)でレビュー中。実際の設定と操作の正本は同PRのskills/clarify-requirements/references/session.mdとし、以下は設計上の配置・候補を示す。

## 実行手段

調査の問いを作る、根拠を選ぶ、選択肢を比較する、人に必要な判断を求めるといった手順は、最初は一つのスキルとして試す。状況によって省略・追加調査・合意待ちが必要になるため、工程ごとのスキル分割や順次実行スクリプトは必須にしない。スキルは判断と道具の使い方を定めるもので、遵守を機械的に保証するものではない。

対話用CLIは保存先の解決、対象と根拠、質問・回答・未解決事項の保存に加え、不足時の停止と回答後の再開を担う設計とする。回答待ちの間は常駐せず、保存して終了し、回答を渡して再開できる形を目指す。十分性の意味的な判断はLLMが行い、CLIは資料や回答の存在だけで充足・合意と判定しない。基準は[コンテキスト十分性](../context-sufficiency.md)を参照する。

合意済みIssue以降の実装・検証・修正は、既存CLIを再利用する。要求合意前の段階を既存のrepair/review状態に無理に当てはめない。固定の工程順ではなく、必要な情報が不足する作業を停止し、不足が解消したか再評価して引き継ぐ。PR #52では保存済みの不足と回答待ちをgateで拒否し、回答後の再評価を必要とする。会話の提示と実装への引き継ぎは担当者が行う。

## 保存先の設定案

設定は対象リポジトリごとに、作業開始時の入力として与える。設定ファイルの名称・配置と読み取り処理は、スキルと保存処理を実装する時点で決める。ユーザー環境全体に探索・注入する設定は作らない。

| 設定候補 | 意味 | 公開試行での候補値 |
| --- | --- | --- |
| `contextDir` | 継続保存する調査記録と、個々の作業途中の記録のルート。対象checkoutの外に置く | `利用者環境の保存先` |
| `referencePaths` | 最初に参照候補を探すリポジトリ相対パス。内容をすべて読み込む指定ではない | `README.md`、`DEVELOPMENT.md`、`scripts/README.md` |

実行対象のリポジトリとcheckoutは別途指定し、相対パスはそのcheckoutから解決する。参照先がなければ不存在を記録する。判断に必須なら確認待ちにし、任意の参考資料なら不足として残す。既存の設計文書・合意済み資産の置き場があれば追加する。Storybookの参照先、UI部品・設計トークン、適切な実装例・テスト、導入版に対応する公式ライブラリ文書も、今回の判断に必要な候補として選ぶ。外部URLと対象版は作業メモへ残し、リポジトリ相対パスの設定とは混同しない。公開用と非公開用のリポジトリで保存先を共有しない。

`contextDir`は一時checkoutを削除しても残せる場所にする。自動でGitへ追加・pushする場所にはしない。現行実装CLIの`runDir`とは役割を分け、実装ログの保存契約は変更しない。今回、この候補ディレクトリの作成や既存資料の移動は行っていない。

## 蓄積する内容

```text
<contextDir>/
  research/             # 完了した調査記録。判断根拠として再利用する候補
  work/<task-id>/        # 作業メモ、選択肢、未確認事項、評価、引き継ぎ情報
```

各段階で固定のファイル一式を生成しない。小さな作業は一つのMarkdownで足り、元資料や合意記録には参照を付ける。初期案は人が読むMarkdownを使い、同じ内容のJSONとMarkdownの二重管理、全文検索DB、自動要約の階層は導入しない。既存の機械出力が必要ならその形式のまま根拠として参照する。機械処理の必要が判明した場合にのみ、構造化する情報と正本を選ぶ。

調査記録には、問い・結論・出典と対象版または確認日・未確認事項・適用範囲を残す。未検証の推測と確認した事実を区別し、評価を行ったかも分かるようにする。調査完了は「合意済み」や「今も正しい」を意味しない。途中で止まった記録はworkへ残し、完了した調査として扱わない。

要求・合意の正本はIssueとその合意記録であり、ローカルメモではない。作業メモからIssueを整備した後はIssueと対象版を参照し、編集可能な要求の正本を二つ持たない。チームで再利用する方針・設計理由は、既存の適切な文書へレビューを通して反映する。既存の置き場がなければ、その必要が生じた時点で小さく設ける。

## 保存と再利用の動き

1. 開始時に設定した参考資料と過去の調査を探し、今回の問いに関係する記録だけ選ぶ。過去の結論は調査の手掛かりとし、現在のコード・契約・合意と照合する。
2. 調査中は出典、確認できた内容、残る問いをworkへ残す。調べた全文を無条件に複製せず、必要な根拠と参照を保存する。
3. 調査を終えたら、依頼のたびにユーザーへ保存を頼ませずresearchへ記録する手順をスキルに含める。初期実装はスキルがarchiveコマンドを呼ぶ手順であり、自動フックではない。
4. 記録から要求・方針を具体化し、必要な判断を得る。合意対象と根拠をIssueへ引き継ぐ。閲覧できない資料を唯一の根拠とする場合は、引き継ぎ先が判断できる共有方法を確認する。
5. 作業で得た知見のうち、継続利用する価値があるものだけ共有文書の更新候補にする。公開範囲・適用条件・現在の根拠を確認し、レビューを経て反映する。

蓄積された全記録を次の作業へ注入しない。古い・矛盾する記録には訂正や後続記録への参照を残し、履歴を残すことと現行の根拠として採用することを分ける。非公開資料を公開試行や別組織の文脈へ自動転記しない。

## 試行で確認すること

保存と検索の手間、同じ調査の重複、古い知見を採用した誤り、根拠への到達性、引き継ぎ時に失われた未確認事項を観測する。蓄積量だけを成功指標にしない。記録が増えても判断や再利用に寄与しない場合は、保存内容や選び方を減らす。

実装の順序は、保存先・参考資料の設定を具体化し、調査から合意までを扱うスキルへ組み込み、最小限の保存・停止・再開処理を用意する。その後に架空の課題で試す。スキル作成そのものと、独立した実モデル実験の実行上限・開始は分けて扱う。
