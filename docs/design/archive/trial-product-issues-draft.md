## Issue A：検索試行の土台となる商品一覧を用意する

### 目的

架空の商品一覧とその動作検証を、人が確認して再利用できる初期資産にする。既存のデザインシステムや部品への合意があるとは扱わない。

### 共通条件

試行リポジトリのREADMEとDEVELOPMENT.mdを参照する。人によるPRレビュー・承認を必須とし、検証の変更理由と検出範囲を説明する。公開可能なコード・架空データのみを使用する。

### 固有の完了条件

- 文書のコマンドでローカル起動できる商品一覧画面を用意する。
- 下記の固定データをすべて表示し、商品名と商品コードを読み取れる。表示順は記載順とする。
- 商品一覧には見出しを付け、商品名・コードの関係が画面とHTMLの構造から分かる。
- 検索UIはまだ追加しない。
- 実際の画面を開くE2Eで、全商品の名前・コードと表示順を確認する。実装の写しではなく要求に対する期待値を使う。
- ローカルとCIの共通 `bun run check` に必要な動作テストを組み込む。TypeScriptを採用する場合は型検証も含める。
- READMEに起動・検証手順とデータの所在を記録し、既存の「アプリ未実装」等の説明を更新する。
- PRに対象commitの画面のスクリーンショット、実行した検証と結果、未確認事項を載せる。画面の構成と読みやすさは人のレビュー対象とする。

## Issue B：合意した商品一覧に名前・コードの検索を追加する

### 目的・開始条件

利用者が商品名または商品コードの一部を入力して商品を絞り込める。一覧のIssue Aがマージされ、再利用する実装・検証を対象commitで特定してから開始する。

### 共通条件

READMEとDEVELOPMENT.md、およびIssue Aで受け入れた一覧・検証を参照する。検索追加で不要にならない一覧の保証は維持する。共通条件をこのIssueへ複製しない。

### 固有の完了条件案

検索欄には「商品名・商品コードで検索」というラベルを付ける。入力のたびに商品名または商品コードへの部分一致で一覧を更新する。検索語の前後空白を除き、英字の大小文字は区別しない。入力のクリアはキーボードで全削除する操作で足り、専用ボタンは必須としない。

| 入力・操作 | 期待する表示（順序も維持） |
| --- | --- |
| 初期表示、空文字、空白のみ | 全4件 |
| ノート | 青いノート、赤いノート |
| 青い | 青いノート |
| `note` | 青いノート、赤いノート |
| `  pEn-001  ` | 黒いペン |
| 存在しない商品 | 商品0件と「該当する商品はありません」 |
| 該当なしの後に入力を全削除 | 全4件に復帰し、該当なしの表示は消える |

- ラベルで検索欄を特定でき、キーボードのみで入力・削除できる。
- 検索結果が変わっても元の固定商品データを失わない。
- 実際の画面を操作するE2Eで上記の利用者の操作と結果を検証する。ロジックの単体テストはE2Eだけでは確認しにくい条件がある場合に追加し、同じ期待値の無目的な二重化を避ける。
- 共通の `bun run check` がローカル・CIで成功する。
- READMEに利用方法と検索仕様を記録する。
- PRで一覧のどの資産・検証を再利用したか、今回変えた部分、人に確認してほしい点を説明する。絞り込み前後の画面証拠を添える。

全角・半角変換、かな変換、複数語検索、曖昧検索、通信、保存済み検索、認証、本番配布は対象外。

## 試行としての評価（機能の完了条件とは分ける）

検索機能の完成だけで開発フローの有効性を結論づけない。実験開始前に次の評価手順と実行経路を確定する。

- 正常な変更：要求、実装、検証結果、独立評価、文書、人の承認が同じ対象commitに対応するか。
- 検証失敗：テスト失敗を成功扱いせず、修正と再検証へ戻れるか。
- 検証後の変更：以前の結果を流用せず、最新commitで再確認するか。
- 文書更新漏れ：動作テストの成功と分けて監査で指摘し、修正後に再確認するか。

障害を与える試行は取り込む変更と分け、失敗例と修正経緯を保持する。まずモデルを使わない制御確認と、実モデルによる修正確認を区別する。未実装の制御が自動で動くとは扱わない。

合意済み上限はAstra/highで実装・修正最大3回、独立評価最大3回、モデル実行の累計待ち時間最大60分。初期資産準備と検索試行の間で上限を暗黙にリセットしない。実行経路、計測方法、実行上限の適用範囲を実験開始前に明記し、usage、時間、介入、未達条件を記録する。今回は比較実験ではなく、料金の上限も意味しない。
