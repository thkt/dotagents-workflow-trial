# 次の判断に進むためのコンテキスト十分性

次に進む判断と、その判断に必要な根拠を整理する設計基準。基準は調整可能とし、使用した版と評価を対応づける。実際の評価項目は[criteria.json](../../skills/clarify-requirements/references/criteria.json)、適用方法は[sufficiency.md](../../skills/clarify-requirements/references/sufficiency.md)、保存操作は[session.md](../../skills/clarify-requirements/references/session.md)を参照する。

## 判断の単位

「情報が十分か」を一般論で評価せず、次に何を決めるかと、その判断に依存する作業を先に明示する。調査を始めるための情報と、実装を始めるための情報は同じではない。必要なコンテキストが不足していれば、依存する判断・作業を進めない。独立して進められる調査は継続できる。

評価項目は充足・不足・適用外のいずれかとし、根拠を残す。未確認は充足に含めず、判断に影響する場合は不足とする。適用外にも理由を付ける。合計点による通過判定は行わず、重要な不足を他項目の充足で相殺しない。

## 共通の基準

| 基準 | 確認する問い | 不足の例 |
| --- | --- | --- |
| 目的の明確さ | 誰の何を改善し、達成した状態をどう確認するか | 実装手段だけ決まり、解消する困りごとが分からない |
| 根拠の適切さ | 出典を確認でき、対象版・適用範囲・鮮度が今回に合うか | 依存ライブラリの導入版と異なるAPI例しかない |
| 必要範囲の充足 | 判断を左右する制約・依存関係・現実的な選択肢を確認したか | 必要なAPI情報が提供されるか未確認 |
| 不確実性の影響 | 未確認事項の答えで、方針・範囲・検証が変わり得るか | 未定の権限条件によって実現方法が変わる |
| 整合性 | 要求・現行実装・方針・合意間の矛盾を解消したか | 共通部品の仕様と画面の要求が衝突している |
| 合意・権限 | 次の作業に必要な対象・範囲の合意と権限があるか | UI案を提案しただけなのに採用済みとして実装する |

全情報の網羅を求めない。未確認事項があっても、今回の判断に影響しない理由を説明できれば残る制約として扱う。LLMの自信の強さ、資料数、検索回数を充足の根拠にしない。

## UI実装に必要なコンテキスト

デザインシステム、Storybook、既存画面、関連テストを探し、今回利用する部品と状態を選ぶ。Storybookの存在自体を必須条件や合意の証拠にはしない。

| 観点 | 確認する内容 |
| --- | --- |
| 対象と対応 | Story・部品・デザイントークンが今回使う実装版に対応するか。試作や廃止予定の例ではないか |
| 適用と合意 | 今回の利用場面が部品の適用範囲に含まれ、利用方針の合意に辿れるか |
| 状態と操作 | 要求に関係する通常・空・エラー・読み込み等の状態、キーボード・フォーカス・画面幅の扱いが分かるか |
| 組み合わせ | 単体部品の既知の挙動に加え、今回の配置・データ・遷移で何を確認する必要があるか |
| 証拠 | 部品の既存検証をどこまで再利用でき、画面接続のE2E・画像・動画で何を追加確認するか |

適用できるStorybookと合意済み部品が揃えば、既知の見た目や挙動を再設計せず、今回の組み合わせと差分に集中する。これはブレを減らすための方針であり、減少量や品質を自動的に保証しない。

Storybookがなくても、現行の部品・テスト・仕様・承認された画面例で必要な判断ができれば進める。見た目しか分からず操作仕様が判断を左右する場合は、その不足を解消する。根拠が足りなければUI案を具体化して合意を得る。Storybookの新設を毎回の前提にしない。

## ロジック実装に必要なコンテキスト

「ベストプラクティス」という評価語だけで採用せず、具体的な実装例・方針・公式文書と、今回に適用する理由を示す。

| 観点 | 確認する内容 |
| --- | --- |
| 入出力と境界 | 型だけでなく、必要な値の制約、失敗、非同期処理、責任の所在が分かるか |
| 適切な見本 | 近いユースケースの現行実装・テストがあり、その設計理由と今回との差が分かるか |
| ライブラリの使い方 | lockfile等で導入版を特定し、対応する公式文書・型・実装で推奨APIと制約を確認できるか |
| リポジトリの方針 | エラー処理、依存の向き、責任分担など今回に関係する規則が分かるか |
| 検証方法 | 期待する結果と失敗条件を、実装の記述方法に依存せず確かめられるか |

既存コードは現状の根拠にはなるが、適切な見本とは限らない。重複、非推奨API、根拠のない型アサーション等をそのまま模倣しない。公式文書も製品の要求やチームの合意を決めるものではない。矛盾する場合は差と影響を調べ、重要な方針変更が必要なら判断を求める。

今回の処理に無関係な設計原則や全ライブラリの文書を読み込ませない。適用する見本・根拠・差分を選び、レビューでも同じ参照を使えるようにする。

## 不足時の動きと再開

事実不足は調査し、目的・優先順位・重要なトレードオフは根拠と選択肢を示して人へ確認する。外部回答やアクセス待ちなら、依存する作業を止める。

記録には、次の判断、適用した基準の版、各項目の評価と根拠、不足の影響、解消方法、止める作業、再開条件を含める。形式のために情報を複製せず、既存の作業メモとIssueを参照する。質問と回答は対応づけ、回答後に不足が解消したかを再評価する。返答の受領だけで充足や合意へ変更しない。

LLMが意味的な十分性を評価し、対話用CLIが不足・回答待ちの保存、依存する作業の停止、回答後の再評価への接続を担う設計とする。CLIは資料や回答の存在だけで充足にしない。一方、誤って充足とされた評価の意味的な正しさまでコードで保証できるとは扱わない。初回試行の独立評価でも、根拠の読み違いと不足の見逃しを確認する。

## 基準の調整

基準はこの文書を正本としてレビュー可能な変更で管理する。利用時にはcommitとパス、未commitなら内容を特定できる保存版などで対象を識別し、ローカルの現行評価と対応づける。基準を変更しても、過去の評価が新基準を満たしたことにはしない。

調整では、進めた結果として不足が原因で手戻りした例と、停止したが確認不要だった例を集める。評価者間で判断が割れた例も、根拠・適用条件・不足の影響を比較する。資料の名称や単語の一致ではなく、判断を支える情報があるかを評価できる具体例を増やす。

実行担当は通過するために基準を緩めない。変更案には理由、見逃しや過剰停止への影響、適用する範囲を示して合意を得る。実行途中で変更する場合は対象版と再評価範囲を明示する。例外も未合意のまま適用外へ振り替えない。
