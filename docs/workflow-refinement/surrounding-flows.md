# 周辺フローの設計案

推奨は、**既存のIssue・PR・基本ドキュメント・evidenceを引き継ぎ先として使い、責任と終了条件の不足を先に埋めること**。固定の工程列や総合管理 CLI は追加しない。優先順は①共有する根拠と整理前の保全、②検証の適用範囲と差し戻し先、③公開から人の承認・マージ後までの引き継ぎ、④必要になった箇所だけの実装変更とする。

## この文書の位置づけ

- **合意済み**：開発の前提。チーム開発・GitHub、全変更の Issue 紐づけ、人が読める大きさの PR、全変更のマージ前の人のレビュー・承認、合意済み資産の再利用、機械・LLM・人の責任分担。
- **調査対象**：`5c5ae81b3d50b1cde202ae1467060a641a436093`。以下の実装に関する説明と根拠リンクはこの版に対応する。採用時には対象版との整合を確認する。
- **提案**：以下の運用・変更候補・試行計画。採用済み方針や実装許可ではない。
- **検証の範囲**：設計の根拠はコード・文書の静的確認と既存の実測記録。運用効果や別clone・別マシンでの再現性は未検証。実際のマージ条件は実行時のGitHub設定で確認する。

検討対象は調査・コンテキスト蓄積、検証・レビュー、説明・公開、マージ後の整理。並行する「要求→質問・回答→Issue 確定」の実測結果は取り込んでいない。その結果が得られたら入口との接続だけ照合する。具体的な方針の採用と実装は、個別のIssue・PRで決める。

## 1. 達成したい状態と最小構成

次担当が元の会話や一時 checkout を持たなくても、要求、使ってよい資産、根拠の適用条件、現在の検証結果、未完了事項を辿れる。人は差分の意図と今回固有のリスクに集中して承認できる。中断やマージ後も、未完了作業と根拠の所在が失われない。

担当は責任の呼び名であり、人数・モデル数・新しい工程を指定しない。同じ人やタスクが複数を担当できるが、実装と独立評価の判断は分ける。工程名ではなく、必要な判断と引き継ぐ情報を基準にする。

| 分類         | 今回の責任                                                      | 正本・既存手段                                                                       |
| ------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| ハーネス     | check・修正・評価の順序、上限、中断、対象変更時の停止を制御する | 必要な試行で使う`correction.ts`、GitHubのマージ条件。通常開発へのCLI一律適用はしない |
| ガードレール | Issueの範囲、人の承認、検証定義を弱めない条件、説明・根拠の要件 | Issue、`DEVELOPMENT.md`、lint・テスト・CI定義                                        |
| 環境         | 実行版・隔離checkout・GitHub・CI・撮影・添付を提供する          | `package.json`・lockfile・設定、Git/gh、Bun、Playwright、必要ならKyoko/FFmpeg        |
| コンテキスト | 要求・根拠・知識と、その適用範囲・合意を渡す                    | 要求はIssue、継続方針は基本文書、調査・実測は記録、PRは変更と承認の記録              |

この 4 分類自体の変更も合意済み資産の変更として Issue・PR で扱う。分類ごとに別のレジストリは設けない。

このリポジトリの設計・計画文書は`docs/workflow-refinement/`に置く。現行方針は基本文書、実測結果は既存の`evidence/`へ残す。設計案をリポジトリに保存しただけで採用済み方針や公開済みとは扱わない。

この設計の入口は本書、次の小さな変更案は[P1 Issue案](p1-shared-evidence-issue-draft.md)。要求・合意の正本は引き続きIssueとする。実行中のcontextDirや生ログはCLIの保存制約に従い、共有に必要な結論・根拠をIssue/PR・evidenceへ残す。

## 3. 調査の蓄積とチーム共有

### 現状で足りる点

`clarify-requirements`は、既存資産の適用条件、出典・版・未確認事項、必要十分性、決定の正本への参照を扱い、調査完了時に記録を保存する方針を持つ。保存依頼を都度求める運用ではない。ただし保存は担当者が`archive`を呼ぶことで行い、バックグラウンド収集の実装ではない。[S1][S2]

現在の`contextDir`は`git-common-dir`に紐づき、同じ Git 管理ディレクトリを使う worktree から新しい task を開始して research を再利用できる。別 clone による同じ保存庫の利用は拒否する。新セッションは旧評価を引き継がない。これらには CLI 入口のテストがあるが、今回は実行していない。[S3][S4]

さらに **#73では、同一ホスト・同じGit共通管理ディレクトリに属する別worktreeへの独立actorの引き継ぎを1例実測済み**。会話履歴を渡さず、Issue URL・共有contextDir・checkout・スキルの場所だけから必要な調査を選び、現行コード・Issue・PR/CIを照合した。旧記録の「実装待ち」を現在の事実とせず、追加実装不要と判断し、新taskでnote→assess→gate→archiveを完了した。要求質問・回答・親への確認依頼は0件で、親の記録には既存11ファイルのハッシュ不変と判断内容の補助なしが残る。保存時のsandbox EPERMは限定した権限昇格で解消している。[S14]

同一の共有保存庫を利用する担当交代は、現行の手段で成立した例として扱う。ただし、完了済みの1要求の再調査であり、未完了要求の精緻化、質問への回答待ちからの再開、別clone・別マシン、一般的な安定性や負荷削減率の証拠にはしない。今回読んだのは保存された担当・親の記録であり、本タスクが実モデルやGitHub確認を再実行したものではない。

### 足りない点と提案

| 現状確認・不足                                                                                 | 影響                                                | 最小の提案                                                                                                  |
| ---------------------------------------------------------------------------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| contextDirは同一Git共通管理ディレクトリのworktree間で再利用できるが、別cloneへの同じ保存庫の利用とチームでの採用管理は対象外 | 同じ保存庫へアクセスできない担当・別マシンにはローカル絶対パスだけでは渡せない | 共有が必要な結論と出典を既存Issue/PRへ、長い記録は既存`evidence/issue-N/`へ置き、Issueからリンクする        |
| ローカルのgate成功は内容評価の保存であり、人の合意ではない                                     | 参考調査を合意済み方針と誤認し得る                  | 調査記録の「参考根拠」と、基本文書・Issueの「採用する条件」を分け、合意者と確認可能な記録へ辿れるようにする |
| 共有記録の鮮度・外部出典の変更は自動検出しない                                                 | 古いAPIや旧要求の結論を流用し得る                   | 再利用時に必要な範囲だけ現行コード・依存版・要求・出典を照合。結論が変われば新しい判断を記録する            |

**提案する使い分け**：個別変更だけに必要な短い根拠は Issue へ直接記載する。再利用価値のある調査は`evidence`の既存構造に簡潔な Markdown で残す。チームで継続使用すると合意した規約は基本文書、再利用する振る舞いは部品・テストへ反映する。全調査を二重保存したり、調査全文を規約へ移したりしない。

この公開試行リポジトリには公開可能な内容だけを渡す。生ログ・内部資料を自動公開しない。非公開の根拠が不可欠なら既存のアクセス制限された共有先を使い、その資料をレビュー担当が読めない状態では依存する判断を止める。新しい共有サービスの導入は現段階の前提にしない。

同一ホスト・同じGit共通管理ディレクトリの別担当には、#73と同様に共有contextDirと現在の対象を渡し、新taskで再評価する。**別cloneや別マシンへの引き継ぎの提案**は、Issue に「この部品・検証をこの範囲で使う」という判断と共有記録へのリンクを置き、受け手は自分の clone・contextDir で新しいセッションを開始する。repo 内の記録を`referencePaths`に指定できる。旧 state や旧 gate をコピーして通過させない。[S2][S3]

## 4. 検証を再利用できる範囲と再確認

**再利用するのは検証定義・固定期待値・既知の適用条件であり、過去の成功を新しい変更の成功へ置き換えない。** 共通 check の実行範囲は現行方針どおり維持する。削減するのは、担当者間の同じ共通 check の重複実行と、説明・レビューの重複である。[S5][S6]

| 再利用する資産                           | 再利用の条件                                                 | 今回追加または再確認するもの                                                                      |
| ---------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| lint・型・書式・複雑度検査               | 対象ファイル・ルール・版の適用範囲が一致                     | 対象外の言語・ファイル、設定や対象選択の変更による検出力への影響                                  |
| 商品一覧・検索のE2E                      | Chromium、指定2画面幅、現在の固定商品と操作の要求に適合      | 新しい操作・状態・組み合わせ・境界。Firefox/WebKit・実機・支援技術・IME途中には成功を一般化しない |
| 合意済み部品・ロジック・デザインシステム | 実装版、状態、入出力、利用場面が一致                         | 今回のデータ、配置、遷移、フォーカスなど接続部分。Storybookの存在だけでは適用済みにしない         |
| 制御CLIの模擬テスト                      | 現行の公開入口を通し、停止・遷移・失敗が対象                 | 実モデルの要求理解、指摘の妥当性、人の回答後の再開、外部サービスの実挙動                          |
| LLMの過去評価                            | 評価対象の要求・差分・根拠が同じと確認できる範囲で参考にする | 要求や意味を変える差分では再評価。機械check・画像の対象から外れる変更なら関連証拠も更新           |
| 画像・操作動画                           | 撮影対象と今回提示する実装が対応し、操作・条件が分かる       | 必要な画面差分と操作を対象commitで取得。動画の成功例で網羅性や人の承認を代替しない                |

商品アプリは JS で、制御 TS 向けの型検査・書式検査の範囲外。商品テストは実装から期待値を生成せず、現在の画面を通す。テスト完了判定は 0 件・未実行・必要集計の欠落を拒否するが、テスト削除・未登録・検証定義の無効化まで意味的に判定するわけではない。[S5][S7]

LLM は、今回の要求を破った実装ならそのテストが失敗するか、必要な境界や失敗を見落としていないか、規約のための不必要な分割・重複検証がないかを監査する。全変更への mutation testing や追加レビュー回数は一律要求しない。人は要求の意図・範囲、既存資産を適用できる条件、残る確認を重点的に見る。

check・独立評価の対象は公開する差分へ対応づける。公開準備で成果物を変えたら関係する検証・評価へ戻す。証拠ファイルや説明だけの追記でも、古い評価が新しい追記まで確認したとは書かない。最終 head の CI と人のレビューは別途必要。snapshot は ignored な依存や生成物を含まないので、撮影・環境の対応は公開担当が確かめる。[S6]

## 5. 失敗・差し戻し・中断の引き取り先

停止理由と担当能力を分ける。`needs_human`という名称でも、直ちにユーザーの価値判断が必要とは限らない。実行担当で解消できる環境・撮影の問題か、範囲・権限・上限の判断が本当に必要かを切り分ける。元の結果は書き換えない。

| 観測した状態                                   | 引き取りと戻る場所                                                                         | 再開条件・残すもの                                                                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 根拠不足、reference先が読めない                | 調査担当が事実を補う。意図が必要なら人に質問                                               | 止めた判断と不足を記録し、現在の根拠で再評価                                                                                |
| checkの非zero                                  | 実装担当がログから原因を調べる。環境障害なら実行担当へ                                     | 最小修正後にホストcheck・独立評価。判定を通すために検証を弱めない                                                           |
| check起動不能・timeout                         | 実行担当が環境・残存プロセスを確認                                                         | 合格でも実装不合格でもなく確認不能。環境復旧後に同じ必要検証を行う                                                          |
| `needs_changes`                                | 指摘が要求のどの未達条件かを確認。コード・テスト・準備証拠は実装担当、公開作業は公開担当へ | 不足が解消した対象で検証・再評価。要求自体の変更なら要求整理へ戻る                                                          |
| 不正応答、actor起動失敗                        | 実行担当がモデル出力・CLIログ・対象を確認                                                  | actorが止まった理由、controllerが止めた理由、成果物の未達を別記。返答形式だけを直して実装成功としない                       |
| 要求・対象が変化                               | 実行担当が並行作業やIssue更新を照合                                                        | 現在の要求と差分の採否を整理し、必要なら人が範囲を再合意。旧成功を流用しない                                                |
| 回数・時間上限、SIGINT/SIGTERM、SIGKILL/OS停止 | 実行担当が実プロセス、stateのactive・回数、ログ、作業差分を照合                            | 既存state/lock/ログを保持。残時間を推測で増やさず、不明なら再実行を止める。既存承認内の残上限を確定できた場合だけ続行を準備 |
| 公開結果が不明、添付が部分成功                 | 公開担当がGitHubのPR本文・添付・headを確認                                                 | 既存PRや成功済み添付を重複作成せず、残る公開作業だけ再実行                                                                  |
| 人の差し戻し                                   | 指摘の中身に応じて実装、説明、要求整理へ                                                   | 解決した差分と回答をPRに残し、最新CI・必要な再評価・人の再承認                                                              |
| マージ後の不具合                               | 実装担当が新しい不具合Issueで原因と影響を整理                                              | 必要な修正・revertもIssue/PRと人の承認を通す。完了済み実行の結果を改変しない                                                |

既存 CLI は中断後の自動復旧や lock 解除を提供しない。新しい run を用意する場合も、旧 run への参照・消費済み量・残り上限・再開理由を既存の試行記録へ残す。追加予算や要求・権限の拡大だけを人へ判断依頼する。新 run で上限を初期化したことにしない。[S6]

Issue #56 では、撮影の対象不明を親担当が解消し、残上限を新実行へ渡した記録がある。その後、公開・人の確認を実装不足に含めた評価で再停止した。Issue #67 の指示変更では、機能不足の`needs_changes`と、準備済み成果物の`accepted`を各 1 回観測している。この古い差し戻し問題を現行の未修正欠陥として再提案しない。ただし人の要求変更後の再開や一般的な誤判定率は未検証である。[S8][S9]

## 6. 説明・公開・人の承認

現行の PR 公開スクリプトは push 済みブランチから App で PR を作成し、同じ head の open PR があれば URL を返す。本文更新・添付・push・承認・マージは担当しない。これは役割の限定であり、全自動化の不足を直ちにコードの欠陥とはしない。[S10]

提案する PR 説明の最小内容は、変わる利用者の結果、必要な理由と範囲、Issue へのリンク、再利用した資産と今回の差分、検証結果・未確認事項、重点的に人が見る箇所。Issue 全文や実行ログ全文の複製は不要。独立して判断できる結果ごとに PR を分け、レビューが困難な大きさなら着手範囲へ戻って分割する。行数の固定上限は作らない。

画面変更には必要な画像、操作・遷移変更には主要手順の動画を用意する。解説音声を使う場合は macOS Kyoko、合成音声であることと操作の対応を示す。図は必要な場合だけ Mermaid を基本とする。添付は現行方針の`gh pr edit --attach`を使い、公開担当が本文 URL と PR 内の画像表示・動画再生まで確認する。撮影済み・添付コマンド成功・表示確認済みを混同しない。[S11]

PR 説明に「ローカル check」「最新 head の CI」「独立評価」「人の確認・承認」を別々に示す。検証定義の変更を含む PR では、守る条件、変更理由、失う検出条件と代替証拠を人が確認する。最新の承認と必須 check が揃っても、GitHub で MERGED を確認するまで整理へ移らない。

本番配布は README で対象外。PR 公開・main へのマージと本番リリースを混同しない。今回 CD やリリース承認工程は追加しない。[S5]

## 7. 整理前に残す情報

要求・合意はIssue、必要な根拠・検証結果はIssue/PRから辿れる共有先へ残す。作業場所を整理する前に、その参照を次担当が開けることを確認する。未完了の作業と必要な記録は保持する。全ログの公開・永久保存や専用の整理工程は要求しない。

worktreeの共有単位や保存制約は既存の`session.md`[S2]、実際の整理はGit標準の操作に従う。archiveによるローカル保存だけでチーム共有が完了したとは扱わない。旧セッションの恒久再開、保存庫移転API、別clone・削除後の専用試行はP1の要件にしない。実際の引き継ぎで不足が出た場合に、その不足だけを確認する。

## 8. 最小の変更候補と不要な追加

以下は計画候補。実測と合意の結果に応じて採否を決め、進行状態は対応するIssue・PRで管理する。

| 優先     | 変更候補                                                                            | 変更先の候補                                                                                                              | 完了を観測する条件                                                                                     |
| -------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| P1 | 共有する情報と整理前の参照確認を短く補う | `DEVELOPMENT.md`を正本とし、`references/session.md`は必要なら参照リンクだけ補う | 次担当がIssue/PRから要求・根拠・検証結果を辿れ、未完了の作業が保持される |
| P2       | 差し戻し理由ごとの引き取り先と、公開・人の残作業の記載を既存説明へ集約              | `scripts/README.md`の担当・再実行・公開の既存節                                                                           | 実装担当が解消できない公開作業を修正ループに戻さず、必要な担当が引き取れる                             |
| P3       | 検証定義の再利用条件と最終対象への対応を既存PR説明で試す                            | まず実際のPR。再現性のある不足だけ`DEVELOPMENT.md`へ反映                                                                  | 過去check、現在CI、LLM評価、人の承認の対象を読み違えず、今回固有の確認が分かる                         |

P1は共有する情報と整理前の確認だけを補う、小さな文書変更とする。別cloneやworktree削除の実測を完了条件にしない。P2/P3 の大半は現行手順で可能であり、説明不足の実例がなければ追記しない。周辺フローを一括改造する PR にはしない。

現段階で追加しないもの：全工程の状態管理器、共有 corpus 専用 DB、資産レジストリ、質問ごとのログ、Issue 本文の機械契約化、全 PR への実験 Issue・図・動画、LLM レビューの固定増員、合格が出るまでの再試行、自動 lock 削除、自動ログ廃棄、contextDir の全内容の自動公開、CD。

## 9. 必要になった場合の試行と完了条件

#73の同一ホスト・別worktree・独立actorの成立例は再試行せず利用する。P1では既存Issue/PRの必要な参照を確認し、文書と現行処理を照合する。別clone・整理後の専用試行は必須にせず、実際の引き継ぎで不足が見つかった場合に確認する。次表はP2以降で必要になった場合の候補であり、P1の完了条件ではない。フロー自体の比較・計測が目的の場合だけ、成果物Issueと実験管理Issueを分ける。[S12]

| 候補                  | 試すこと                                                                                                                         | 証拠・完了条件                                                                                                                       | 不成功の場合                                                                          |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 検証と公開への接続 | 次の小さな実変更で既存検証を再利用し、LLM評価・公開担当・人へ渡す                                                                | 要求の未達は実装へ、添付/表示は公開担当へ、人の意図判断は人へ届く。最終headのCI・承認を区別して残す                                  | 指摘の根拠と戻り先を見直す。判定が期待と違っただけで評価者を増やさない                |
| 中断からの引き取り | 制御可能な隔離試行で1回の中断を扱う。自然発生の中断で十分な証拠があればそれを使う                                                | 子プロセスと書込の停止状態、消費量、残上限、再開担当を照合し、上限を初期化せず次へ進める。人の判断待ちを試す場合は実際の回答まで確認 | 事実不明なら保留する。単なる環境復旧を人の要求変更後の再開成功としない                |

各試行はまず 1 例の成立確認であり、品質・速度・レビュー負荷が一般に改善したとは結論しない。記録するのは対象版・条件・引き渡せたもの・補足の回数と内容・実際の停止理由・未確認事項程度でよい。専用テレメトリは追加しない。

この設計を運用として採用できる完了条件は、必要な根拠と担当が引き継がれ、要求を満たす実変更を人が承認してマージでき、整理後も必要な参照が残ること。#73で独立actorの引き継ぎ1例と質問・親への確認依頼0件は観測済み。ただし一般的な引き継ぎ負荷、真の要求変更後の再開、別clone・別マシンでの再現は現時点で未実測とする。

## 10. 残る人の判断

現時点で、この設計文書の完成を妨げる追加質問はない。既に合意した GitHub・公開可能な試行データ・人の承認の方針で、共有先と担当の最小案を具体化できる。

P1を共有情報と整理前の確認に絞る方針は合意済み。具体案は[p1-shared-evidence-issue-draft.md](p1-shared-evidence-issue-draft.md)にまとめる。次はIssueへの反映を判断し、別clone試行の対象・上限決めを先行条件にしない。非公開資料の外部共有、新しい共有サービスの導入、生ログの廃棄、既存予算の拡大が実際に必要になった場合にだけ、その対象と影響を提示して人へ判断を求める。今回、それらを推測で決めたり一律の質問項目にしたりしない。
