# implementで文書整備を扱う計画

[Issue #82](https://github.com/thkt/dotagents-workflow-trial/issues/82)で、文書のみの変更と実装に伴う文書更新に共通の判断基準を適用する。変更・検証結果と採用状態はIssue・PRで管理する。

## 目的と責任

次担当が元の会話を知らなくても、現在の使い方・開発方針・判断理由・検証範囲を辿れる状態を保つ。文書のみの変更も、合意済みIssueから成果物を整えて検証・評価・公開へ進むimplementの対象とする。

根拠は[アウトカム案](../design/OUTCOME-draft.md)、[開発方針案](../design/development-policy-draft.md)、[周辺フローの設計案](surrounding-flows.md)。採用済み方針は[DEVELOPMENT.md](../../DEVELOPMENT.md#ドキュメントの更新)を優先する。共有・整理前の保全は既存方針と[P1案](p1-shared-evidence-issue-draft.md)の採用範囲を確認し、ここで再定義しない。

| 依頼 | 担当・入口 |
| --- | --- |
| 合意済みの文書整理Issue | implement。文書を成果物として同じ検証・独立評価・公開へ渡す |
| 実装に伴う文書更新 | implementの成果物と完了条件に含める |
| 何を文書化するか未確定の相談 | 要求整理。変更範囲が合意されればIssueへ反映する |
| 文書のレビューだけ | レビュー。変更や公開を依頼されたと読み替えない |

文書専用スキルや独立した制御ループは設けない。文書の正確さ・重複・読む順序の判断は共通方針へ集約し、implementの初回実装・修正・独立評価が参照する。

## 確認した構成

基準はmain `7fffbf0`（PR #86を含む）。[implement](../../skills/implement/SKILL.md)は[scripts/development.ts](../../scripts/development.ts)へ委譲し、初回実装の指示はREADME・DEVELOPMENT.mdを読む。修正と独立評価は[correction.ts](../../scripts/correction.ts)が担い、評価は必要な文書を対象に含む。コード変更があることを公開条件にはしていない。

文書のみでも既存の共通checkを適用する。HEADからの差分と未追跡ファイルが`.md`のみなら既存媒体を保持し、撮影・媒体の置き換えを省略する。その他の変更や判定不能時は通常の撮影へ進み、必要な証拠の不足・不整合は独立評価で確認する。

## 実施する変更

1. DEVELOPMENT.mdに、要求確認時と差分確定時の更新要否判断、正本への反映、説明と根拠・関連リンクの確認を定める。更新不要も理由を短く示して選べるようにする。
2. implementが文書のみの変更を扱うことを入口に明記し、初回実装・修正・独立評価から共通方針を参照する。コードや新しいテストが不要なIssueに、それらを一律要求しない。
3. README・制御CLI手順・設計の入口を上記の分担に合わせる。既存の公開権限・人のレビュー・承認の扱いを保持する。

完了条件は、文書単独と実装に伴う更新の双方で、読者・更新理由・正本・確認方法を特定でき、必要な文書不足を修正へ戻せること。未合意の仕様判断は要求整理へ、PR公開・添付と人の承認は担当へ引き継ぐ。文書整理を理由に要求の範囲や検証基準を変更しない。

## 検証と実測

変更時は既存の `bun run check`、スキルの標準検証、変更箇所に関係するリンクと現行実装・方針の照合を行う。文言一致だけのテストは追加しない。

文書のみの小さな実課題1件をimplementで実行する。対象Issueは読者の困り事と文書の完了条件を定め、実験の回数・時間上限・観測事項は実行記録に分ける。既存上限（モデル累計20分、追加修正2回・独立評価2回、check等各9分）を維持し、まず `--no-publish` で生成差分と評価を確認する。記録・消費量・停止理由を保持し、失敗時に同じ試行を別名で再起動しない。原因を修正した版の確認は、旧runを保持し、版・変更理由・上限を明記した別試行として扱う。

確認するのは、要求に沿った文書変更が生成されること、不要なコード・テスト変更を加えないこと、共通checkと独立評価を経ること、対象と未確認範囲を正しく引き継ぐこと。既存撮影による媒体差分などが生じれば、成果物要求への影響と制御側の原因を分けて記録する。公開しない試行をPR公開・人の承認・マージの成功証明にはしない。

実装に伴う文書更新は[PR #84](https://github.com/thkt/dotagents-workflow-trial/pull/84)の記録を参照する。媒体の準備状態と文書の不整合を独立評価が指摘し、修正へ戻した例がある。ただし今回追加する共通方針の実測ではないため、その適用確認と既存フローの実績を区別する。

補助的に、説明へ影響しない内部整理では更新不要、未合意の仕様変更では要求整理へ戻る判断を机上確認する。実例1件の成立を一般的な安定性の証明にはしない。

実施した文書単独の確認と、ホスト撮影の原因修正前後の結果は[実測記録](../../trial/evidence/documentation-flow.md)を参照する。
