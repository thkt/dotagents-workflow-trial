# ドキュメント整備フローの計画

2026-09-11作成。文書整備を単独で進める入口と、implement完了時の必要な文書更新を接続する計画。計画作成後、依頼者の「一旦このまま進めてみて」を受け、[Issue #82](https://github.com/thkt/dotagents-workflow-trial/issues/82)で共通方針と単独入口を具体化する。採用状態・変更・検証結果はIssueとPRで管理し、計画の保存だけで全段階が実施済みとは扱わない。

## 目的と前提

次担当が元の会話を知らなくても、現在の使い方・開発方針・判断理由・検証範囲を辿れる状態を保つ。実装で必要になった更新を完了前に揃え、既存文書の不整合だけを直す依頼も同じ基準で扱えるようにする。

根拠は[アウトカム案](../design/OUTCOME-draft.md)、[開発方針案](../design/development-policy-draft.md)、[周辺フローの設計案](surrounding-flows.md)。採用済みの方針は[DEVELOPMENT.md](../../DEVELOPMENT.md#ドキュメントの更新)を優先する。

確認対象はローカルHEAD `201b13657864861b64e5d455e65bd9e084812084`。READMEには読む順序と正本の分担、DEVELOPMENT.mdには文書更新・合意・記録の原則、scripts/README.mdには文書を含む独立評価の責任がある。不足は、更新要否の判断から反映・確認までを担当者が実行できる一続きの手順である。

implementは別タスクで検証中。着手時に、別worktreeの未コミットの `skills/implement/SKILL.md` が `scripts/development.ts` へ実行を委譲する構成を確認した。このcheckoutの基準版の実行入口は `scripts/correction.ts` と `scripts/codex-actor.ts`。implementの確定版・検証結果を後続の接続前に確認し、進行中のファイルをこの変更へコピーしない。

## 対象と分担

今回扱うのは、変更に伴う文書の影響判断、正本への反映、陳腐化・重複の整理、根拠との照合、およびimplementへの接続である。

[P1](p1-shared-evidence-issue-draft.md)の共有先・整理前の保全は参照して利用し、同じ規則を再定義しない。要求整理は合意と完了条件をIssueへ渡す責任、implementは成果物と必要な文書更新を揃える責任、公開担当はPR本文・添付・閲覧確認、人は要求変更と最終レビュー・承認を担う。

新しい総合CLI、専用台帳、全文書の毎回監査、定期実行、文書量による合格判定は追加しない。新たな方針の採用が必要なら要求整理に戻し、文書整理の裁量で決めない。

## 共通の進め方

| 判断・作業 | 担当が確認すること | 出力・次へ進める条件 |
| --- | --- | --- |
| 入口を確定する | 文書単独なら読者・困り事・対象と根拠、implementからならIssue・変更差分・検証結果を読む | 今回の文書で解決することと範囲が分かる。単独変更も既存の要求整理を使いIssueに紐づける |
| 更新要否を判断する | 操作・仕様・設定・制約・開発方針・判断理由のどれが変わるか、既存のどの説明に影響するか | 更新先と理由を特定する。影響がなければ更新不要と短く説明できる |
| 根拠を照合する | 現行コード・設定・実行入口・対象版の検証結果と、Issueの合意を確認する | 事実・提案・合意・未確認を区別できる。不足があれば依存する記述を保留し、調査や人の判断へ戻す |
| 正本を更新する | 現在の説明として書き直し、周辺文書は必要なリンクと概要にする | 古い記述や重複を整理し、残す履歴・証拠への参照を保つ |
| 検証・評価する | 読む順序、変更箇所と参照元のリンク、例・コマンド・説明と根拠の整合を確認する | 要求を満たし、確認できない範囲を明示する。文書の未達は修正、仕様の矛盾は要求整理へ戻す |
| 公開へ引き継ぐ | 更新した正本、対象と確認結果、残る担当作業をPRで説明する | 公開担当と人が変更を評価できる。マージと整理は既存の周辺フローへ接続する |

短い更新要否の理由や確認結果は既存のPR説明・評価結果に含める。全変更で別の文書一覧や報告ファイルを作ることは求めない。

### 反映先の選び方

| 情報 | 正本・反映先 |
| --- | --- |
| 合意した個別要求・完了条件・変更範囲 | Issue |
| 現在のセットアップ・利用方法・共通検証範囲 | README |
| 継続的な開発・レビュー方針 | DEVELOPMENT.md |
| 制御CLIの操作・実行制約 | scripts/README.md |
| 再利用する設計判断・理由・適用条件 | docs/design/。提案と採用済みを明示し、設計の入口から辿れるようにする |
| 個別の変更説明・確認結果 | PR。長い検証記録はtrial/evidence/へ置き参照する |
| ローカル作業中の調査 | 既存contextDir。チームに必要な結論は現行の共有方針に従う。P1の追加案は採用範囲を確認する |

計画が実施された後は、現行手順を基本文書へ反映し、この計画に実行ログを積み重ねない。設計案を移す・整理する場合も、必要な判断根拠と参照を保持する。

## 変更単位と順序

### 1. 更新判断と完了条件を既存方針に接続する

最初の小さなIssueで、DEVELOPMENT.mdの「ドキュメントの更新」に更新要否を判断する場面と完了条件を補う。READMEやscripts/README.mdは必要な参照だけを追加する。P1の最新差分を照合し、共有・保全の重複を避ける。

完了条件は、文書単独と実装に伴う更新の両方で、読者・更新理由・正本・確認方法が分かること。更新不要も根拠を持って選べ、表現を現行コードに合わせる作業と未合意の仕様変更を区別できること。

### 2. 文書単独の入口とimplementの完了確認をつなぐ

単独の「文書を整備して」という依頼から共通手順を実行できる、短い再利用可能なスキルを追加する案を第一候補にする。方針本文は複製せず、既存の要求整理と正本を参照する。名前・配置は着手時のスキル構成に合わせて決める。

implement側では、要求確認時に文書への影響を見立て、差分が揃った時点で見直し、必要な更新を独立評価の前に含める。独立評価は更新漏れ・古い説明・過大な保証を確認する。更新後に成果物が変われば関係する評価へ戻す。

着手前に別タスクのimplement成果のcommit、入口、担当分担、完了条件と実測の未確認事項を読む。既に同じ判断があれば再利用し、追加箇所だけを変更する。制御の状態・結果schemaは、現行方式では必要な停止や差し戻しを表せない具体的な不足がある場合に限って変更する。

完了条件は、単独入口とimplementの双方が同じ更新基準を参照し、必要な文書が不足した対象を公開準備完了と扱わないこと。PR添付未実施や人の未承認は、文書内容の不備とは分けて引き継ぐこと。

### 3. 実例で二つの入口と引き継ぎを確認する

文書単独の小さな実課題1件と、文書更新が必要なimplementの実変更1件で確認する。別タスクの試行が後者を満たせば、その証拠を再利用する。補助確認として、内部整理など更新不要の差分1件を机上で判断し、無意味な追記を要求しないことを確認する。

各試行では、Issue、対象commit、更新の判断、根拠、独立評価の指摘と対応、介入した理由、未確認事項を必要な範囲で残す。実モデル実行の回数・時間上限は着手時に既存の承認範囲を確認し、範囲外なら具体的な試行内容と合わせて確定する。

完了条件は、元の会話を持たない評価担当が現在の操作・判断理由・未確認範囲を辿れ、文書の不整合を根拠付きで差し戻せること。公開後は人のレビュー・承認・実際のマージを区別し、整理後も必要な参照が残ることを確認する。1例の成功を一般的な安定性の証明にはしない。

## 検証の扱い

文書・スキルの評価では、説明と現行実装・合意の照合、変更対象に関係するリンクと読む順序の確認を行う。コード変更が必要なら、現在の公開入口を通じた振る舞いの検証を追加する。文言一致だけのテストは作らない。

各実装PRの提出前は既存の `bun run check` を使う。check成功とは別に文書の正確さ・有用性を評価する。操作確認は対象と副作用を見て選び、公開・削除コマンドをリンク確認のために実行しない。

この計画案自体はリンク・既存方針・範囲と完了条件の整合を確認する。計画保存の確認と、今後のフロー実測成功は区別する。
