# 正規 `.agents` 運用への移行案

現時点では、実行環境にある既存の `.agents` ディレクトリを、この試行用リポジトリ（repo）で上書きするための条件は揃っていません。私たちは、新しい `scoping`（要求調査・設計用の構成要素）と `implement`（実装・検証用の構成要素）を移行の候補として扱います。既存の実行環境、データ保存状態、および検証の証拠を保持したまま、対象のリポジトリ（repo）、登録方法、GitHub等へ書き込みを行うアカウントやアプリケーションといった公開主体、さらに移行時に引き継がない保証事項を決定した上で、切り替えを判断します。本書は、その判断を行うための比較と準備案です。実際の移行手順を実行する許可を示すものではありません。

## 位置づけと確認範囲

関係者が**合意済み**である内容は、この移行案の作成と検証、および設計の案内文書（入口）への追加のみです。依頼者がCodexとの会話で承認した範囲については、本Issue「docs: 正規agents運用への移行案を現行資産に基づいて作成する」に記載された目的・合意、変更範囲、完了条件を正式な決定資料であるマスター文書（正本）とします。ツールの登録切替、既存資産の削除、コードや設定の変更、および実際の移行処理については合意していません。今後の継続方針は [DEVELOPMENT.md](../../DEVELOPMENT.md) に、周辺の責任範囲に関する検討は [周辺フローの設計案](surrounding-flows.md) に従います。本書ではこれらを再定義しません。

本文中で使用する用語の定義は以下の通りです。「事実」とは、2026-09-12の時点でコード、設定ファイル、文書を読み取って照合した定義を指します。「提案」とは、今後の採用判断が必要な移行先の案を指します。「未決定」とは、その採用判断がまだ行われていない事項を指します。「未検証」とは、実際に動作確認を行っていない事項を指します。また、コードから推測した事項については、「推論」と明記します。

## scoping・implementとの実際の対応

旧環境における処理の「停止」や「再開」の保証は、対応する実行時環境（runtime）と自動実行処理（hook）が取り決め通りに動作する条件のもとで提供される実装上の保証です。したがって、実行ホストシステムへの適切な登録確認の代わりになるものではありません。新環境のスキル定義文書に記載されている担当者の行動手順と、コマンドラインツール（CLI）が機械的に処理を停止させる条件は、明確に区別して読み取る必要があります。

| 入口と責任 | 旧の出力・停止・戻り先 | 新の出力・停止・戻り先と差分 |
| --- | --- | --- |
| 要求調査：依頼と対象repo | 旧環境のResearch処理は、起動時に作成した状態の複製（snapshot）に対する根拠を静的に検証し、第三者として監査を行って報告を確定します。不明な点は未知として残し、監査を受けた人間の判断が必要な場合は待機します。Think処理で事実確認が不足している場合は、Research処理へ戻ります（旧1・旧2） | 新環境では、scopingの担当者が現行の資産・根拠資料（出典）・情報の十分性を調査し、note、assess、gate、archiveの各サブコマンドで状態を保存します。discovery CLIはAIモデルを起動せず、評価内容の真実性を自動判定しません。事実確認が不足している場合は調査へ戻し、依頼者の意図や適用範囲の確認が必要な場合は人間へ戻します。独立評価は必要な場面で選択して利用するため、旧環境のようにすべての報告に対して必須で行われる監査ではありません |
| 要求・設計と人の合意：根拠と未決定事項 | 旧環境のThink処理は、計画書（Plan）または独立評価済みの質問文を出力します。ユーザーからの回答は所有者に紐づけて元の入力データへ記録し、同一の実行状態・snapshot・割り当て予算のもとで処理を再開します。回答が得られない場合は先へ進まず、また回答を得たことだけを理由にIssue作成権限や投稿権限（Ship権限）を勝手に拡大させることはありません（旧2） | 新環境のscopingでは、チャット上で人間からの回答を待ち、決定したマスター文書（正本）、適用範囲、合意者をIssueなどに記録します。noteコマンドを使用して過去の評価を無効化し、再評価を実施します。質問ごとの専用記録ファイルは作成せず、discovery gateは保存済みの評価データのみを参照します。システム全体として、質問の表示・回答の受領・実装処理の起動を強制する自動化の仕組みではありません |
| Issue公開：要求・範囲の合意 | 旧環境では、明示的なIssue作成権限と準備完了状態（ready）のThink Planに基づき、人間が読みやすい本文と全く同一内容の標準形式JSON計画データ（canonical JSON Plan）を生成します。静的検証および独立した忠実性評価を経た上で、Issueの新規作成（create）や更新（update）を行います。計画（Plan）を変更する場合はThink処理へ戻り、GitHub APIの応答結果が不明な場合はIssue側にデータを保存して処理を停止します（旧2） | 新環境では、scoping担当者が既存のGitHub CLI（gh）を使って重複するIssueがないか調査し、本文の作成・公開・再確認を行った上で、参照情報をnoteに記録します。公開範囲は依頼内容に従い、単なる提案にとどまる場合はリポジトリ（repo）内のドキュメント作成で完了します。discoveryコマンドからの直接公開やimplementの自動起動は行われません。旧環境に存在した公開意思の記録（intent）、保留中の書き込み状態（pending write）、忠実性評価といった機械的保証は新CLIにはありません。不明な応答結果の照合や重複防止の責任は、担当者が担います |
| 実装：選択した公開Issue | 旧環境のBuild処理は、開始時にIssueを1回読み込み、唯一存在する `## Plan` セクション内のJSONデータを実装におけるマスター文書（正本）として固定します。すべての実装範囲を単一の実行主体（actor）が実装し、自己評価を行います。想定外の判断が必要な引き渡し（handoff）が発生した場合は独立評価を実施し、事実確認はResearch処理へ、設計確認はThink処理へ戻します。計画案を変更する場合は、旧Build処理を停止させたまま、別途Issueの更新許可と新しいBuildの実行が必要となります（旧2・旧3） | 新環境のimplement処理は、オープン状態（OPEN）のIssueからタイトルや本文（title/body）などの全文を取得し、変更のないコミット済みHEAD（cleanなcommitted HEAD）から独立した作業ツリー（隔離worktree）を作成します。初回実装を行ってから自動修正・評価（correction）に進み、途中で要求の変更が生じた場合は処理を停止します。適用範囲や権限に関する判断が必要な場合は、`needs_human` 状態を出力して人間やscoping担当者へ処理を戻します。新環境にはJSON Plan専用の解析器（parser）や、旧環境のような状態が保存された子プロセスへの自動往復機能はありません |
| 検証と独立評価：実装済み対象 | 旧環境ではBuildとCodeで共通の実行プログラム（executor）がシェル上のテストと独立した意味論的評価を実行し、対象のソースコードや配信処理（dispatch）に結果を紐づけます（束縛）。検証が失敗した場合は実装を行う実行主体（actor）へ差し戻して再検証を行います。最終的に確定した結果に基づき、Build処理はコミットを実行し、Code処理はGitの公開操作を行わずに終了します（旧3） | 新環境では実行ホストが共通のチェック処理（check）や必要な画面撮影を実行し、読み取り専用の別実行主体（read-only actor）が要求全文・コード・テスト・ドキュメント・検証証拠を評価します。失敗した場合は修正→check→評価のサイクルに戻ります。実行回数の上限、制限時間、不正な応答、評価対象の変化、あるいは環境障害が発生した場合には処理を停止します。出力される `ready_for_human_review` はローカル環境での引き渡し準備完了を示しているだけであり、人間による最終承認を意味するものではありません（[制御手順](../../scripts/README.md#結果と再実行)） |
| PR公開：検証済み変更と公開権限 | 旧環境では、Build呼び出し時に明示された投稿許可（Ship許可）に基づいてリモートへの送信（push）や下書きプルリクエスト（draft PR）を作成します（公開除外の指定を尊重します）。これはIssueの公開とは独立した別個の権限です。保留されていたGit操作やPRを照合して処理を再開し、要求された画像データは検証・署名済みバイト列（seal済みbytes）と照合します（旧1・旧3） | 新環境では、implementの依頼に含まれる公開指定の範囲内でコミット、既存のGit認証を用いたpush、GitHub Appを用いた通常のPR作成、既存のGitHub CLI（gh）によるメディア添付、およびCIの動作確認を行います。`--no-publish` オプションを指定した場合は、コミットの実行自体も省略します。公開の成功可否が不明な場合は処理記録を保持した上で担当者が手動で照合を行い、自動再開は行いません。表示内容、動画再生、配置に関する調整が必要な場合は、公開担当者へ戻します（[公開手順](../../scripts/README.md#prの公開)） |
| 人のレビュー・承認：最新PRと証拠 | 旧環境においてShip処理が完了したことや下書きPR（draft PR）が作成されたことは、人間が承認したことやマージされたことの証明にはなりません。旧環境のcleanup処理においても、GitHub上でのマージ完了状態（MERGED）と検証済みの投稿証明（Ship receipt）をそれぞれ別々に確認します（旧3・旧4） | 新環境では、すべての変更に対して人間によるレビューと承認を求め、最新のCI実行結果や会話スレッドの解消状態などを実際のGitHubのリポジトリ設定に基づいて確認します。指摘を受けた場合、実装の不足であれば実装担当へ、説明や添付ファイルの不備であれば公開担当へ、要求範囲の変更であればscoping担当へ戻します。自動での承認やマージは一切行いません（[方針](../../DEVELOPMENT.md#ciとmain保護)） |

旧環境で公開されたIssueや計画（Plan）を新環境へ引き継ぐ際は、既存の本文、合意事項、根拠資料（出典）、および未完了の作業項目をそのまま保持し、今回実装を行う全文と検証条件を担当者が手動で照合します。データが旧形式であることを理由に要求仕様を削ったり、新環境の gate チェックに成功したことだけをもって旧環境の第三者監査済みPlanと同等であると見なしたりしてはなりません。新環境においてドキュメントの修正のみを扱うIssueであっても、同じ実装・検証・評価の呼び出し口（入口）で処理します。ただし、コードの変更、テストの追加、画面撮影などが不要な場合は、これらを無理に追加しません。

## 実行先・ホスト・公開主体

| 論点 | 確認した定義と移行前の不足 |
| --- | --- |
| 対象repo | 旧環境の実行時状態（runtime）はGitの作業ツリー（worktree）と対象リポジトリ内の `.codex/OUTCOME.md` ファイルの存在を必須条件としており、特定の所有者やリポジトリ名（owner/repo）を制限する許可リスト（allowlist）は見当たりません。Code処理ではコミット前のリポジトリも取り扱います。新環境のdiscovery機能はGitの管理ディレクトリに対してデータ保存場所を関連付け（束縛）ますが、リポジトリ名自体は固定しません。これに対して、新環境のdevelopmentおよびpublish処理は `thkt/dotagents-workflow-trial` リポジトリ専用に作られており、公開対象のmainブランチ、GitHub App、インストールID（installation）、リポジトリIDも固定されています。`--repo` オプションは機能を汎用化するための切り替えスイッチではなく、単に対象のローカルディレクトリ（checkout）を指定するだけのパラメーターです（旧5・旧6、[development](../../scripts/development.ts)、[publish](../../scripts/publish.ts)） |
| スキル検出・CLI登録 | 旧環境では6つのスキルの設定ファイル（yaml）、11個のパッケージ実行ファイル（package bin）、および `hooks.json` を定義していますが、これらが実際にシステムにインストールされ、環境変数PATHで名前解決可能になり、イベント登録が完了していることまでは証明されていません。`.skill-lock.json` も実際の登録状態を測定した記録ではありません。新環境では、Git追跡対象である `.agents/skills/scoping` および `implement` の相対シンボリックリンク（symlink）が、それぞれ `../../skills/` にあるマスター文書（正本）に解決されます。ルート直下の `package.json` に実行ファイル（bin）の定義はありません。新旧のツールが同時に検出された場合の動作、優先順位、他のリポジトリから検出されるか否かについては検証されていません。今後、具体的な登録方式と、旧コマンドを保持する期間を決定する必要があります（旧1・旧5・旧7、[新の入口](../../README.md#要求整理とissue作成)） |
| hookとの結合 | 旧環境の自動実行処理（hook）は、入力先頭の `$research` などの明示的な指示、カレントディレクトリ（cwd）、セッションID（session_id）、およびBash形式のイベントとコマンドとの関連付け（束縛）を利用します。編集直後処理（post-edit）は、旧環境が導入されていたツールの設定に基づいて編集ファイルを自動修正します。新リポジトリのスキルは新たなhookを追加しません。現在使用しているホストツールの名称やイベントによって旧hookが意図せず起動してしまわないか、あるいは切り替え後のファイルに対して旧環境の自動整形が誤って作用しないかについて、登録担当者が確認を行う必要があります（旧5） |
| 依存とOS | 旧環境はBun 1.4.0、バージョン固定されたCodex SDK、インストール済みの `codex` コマンド（PATHまたは環境変数 `CODEX_CLI_PATH` で指定）、Git、GitHub CLI（gh）、SQLiteを使用し、シェル上の検証処理は `/bin/zsh` に依存しています。新環境はBun 1.4.2、バージョン固定されたパッケージ、外部の `codex` CLI、Git、gh、Playwright/Chromium、およびmacOS/Linuxのプロセスグループ機能を使用します。使用するAIモデルは旧環境・新環境ともにコード上 `Astra/high` と指定されています。新環境の公開処理はmacOSのログインキーチェーン（login Keychain）および `/usr/bin/security` コマンドに依存しています。そのため、LinuxのCI環境でテストが成功したとしても、それが公開処理全体の他OSへの移植性を示す証明にはなりません（旧3・旧6・旧7、[actor](../../scripts/codex-actor.ts)、[セットアップ](../../README.md#セットアップと検証)） |
| 認証と公開主体 | 旧環境内部でのghコマンド呼び出しは、Issue公開権限とBuild Ship権限を区別して管理していますが、実際にGitHub上で操作を行う主体（公開主体）は実行ホストの認証設定に依存します。旧SDKが使用する非公開のホームディレクトリ（private home）は既存の `auth.json` を利用し、シェル検証処理ではGitHubトークンの環境変数とghの設定を他の処理から隔離します。一方、新環境のscopingにおけるIssue公開および画像等の添付は既存のghコマンドを使用し、push操作はGitの認証設定を使用し、PR作成は限定トークンを発行・即時失効させる固定のGitHub Appを使用します。これら全体を単純に「Appによる公開」と一括りで表現してはなりません。実際のログインアカウント、アクセス権限、暗号鍵の有効性、およびトークン失効失敗時の対応策について、公開担当者が確認を行う必要があります（旧6、[publish](../../scripts/publish.ts)、[公開手順](../../scripts/README.md#prへの画像動画の添付)） |
| 作業と信頼する制御コード | 旧環境は、状態の複製（snapshot）、リポジトリの隔離（repository isolation）、および非公開のデータ保存領域を使用します。新環境のdevelopment処理は、外部の実行データ保存用ディレクトリ（runDir）内に作業ツリー（worktree）を作成し、実行主体（actor）によって編集されない安全な場所から制御コードと設定ファイルを呼び出して実行します。ただし、新環境のactorに指定された `--ignore-user-config` やサンドボックス（sandbox）設定があるからといって、実行ホスト上の秘密情報、すべての設定、同権限ユーザーによる任意のファイル改変まで完全に隔離できると過信してはなりません。GitHub Appの秘密鍵や書き込み権限付きトークンをactor側に渡さない運用を維持します（旧3・旧6、[制御手順](../../scripts/README.md)） |

コードから推測される事項（推論）として、単にディレクトリ名を `.agents` に変更するだけでは、対象リポジトリ（repo）の固定化問題、自動実行処理（hook）のイベント形式、認証の経路、および検証処理における試行環境（trial）への依存関係は解消されません。正規運用をこの試行repoのみに限定するのか、あるいは他のrepoでも使用できるように汎用化するのかは、未決定のままです。もし後者を選択する場合は、コード、設定ファイル、検証方法の変更について、別途Issueを作成して合意を得る必要があります。

## 保存データ・実行状態の互換性

| 資産 | 旧から新への扱い（提案）・保持理由 |
| --- | --- |
| 共有する調査 | 旧環境では `research/records/<research_id>.json` が公式なマスターデータ（canonical原本）であり、`research/reports/` がそこから生成されたMarkdownファイルです。第三者による独立監査や公開安全性の監査データと対（ペア）にして整合性を検証し、知識ベース（Knowledge）は再構築が可能な検索用インデックスとして機能します。ただし、旧環境の基準コミットにおいて `records/` や `reports/` 内でGit追跡されているファイルは `.gitkeep` のみであり、過去の調査報告が保存済みであるとは主張できません。新環境では、コンテキスト保存ディレクトリ（contextDir）内の `research/` にセッション情報やリビジョン番号付きのMarkdownファイルを保存し、IssueやPR、検証証拠（evidence）で共有します。新環境には自動での蓄積データ（corpus）検証、公開安全性監査、知識ベース検索の機能はありません。旧環境のデータのペア構成と変更履歴（来歴）をそのまま保持し、新環境へは選択した根拠と適用条件への参照情報のみを引き継ぎます。旧環境のファイルを単にコピーしただけのものを「再監査済み」と扱ってはなりません（旧2・旧6、[新の保存手順](../../skills/scoping/references/session.md)） |
| 旧private artifacts | デフォルトの設定では、実行対象リポジトリ（repo）内の `.codex/workflow-artifacts/` に保存されます。環境変数 `CODEX_FLOW_ARTIFACT_DIR` が指定されている場合は、リポジトリの実体パスから生成したハッシュ値で保存先を区別します。Research、Think、Issueの各処理で出力された非公開の報告書やインデックス（private artifacts）を保持します。cleanup処理はこの環境変数による上書き設定（override）に従わず、メインの作業ツリー（primary worktree）内の `.codex/workflow-artifacts/cleanup` ディレクトリを専有するため、復元用参照（recovery refs）や復元用一時領域（staging）についても別途状態を確認します。状態の複製（snapshot）、実行主体（actor）の送信データ（payload）、検証記録、公開証拠は、実行時環境（runtime）などの実際の保存場所と合わせて保持します。リポジトリ内部に非公開データを保存する場合は `.gitignore` などの制約が存在するため、Research処理が公開時の重複を防ぐために使用するロックファイル `/tmp/codex-research-publication-locks-<repo実体パスのSHA-256>` についても状態確認の対象とします。新環境の公開用検証証拠（evidence）ディレクトリへすべての内容を移動させてはなりません（旧6） |
| 旧runtimeと進行中の実行 | デフォルトの設定では、OSの一時ディレクトリ領域 `codex-flow-runtime-<uid>/<run-idのhash>/` に保存され、環境変数 `CODEX_FLOW_RUNTIME_DIR` で場所を変更できます。ここには入力データ、処理の目的（intent）、実行状態、質問への回答、子プロセスの実行記録、再実行（retry）の予算制限、保留中の公開処理（pending publication）、および所有権管理データベース `ownership.sqlite` とそれに関連するファイルが保存されます。新環境側には、これらを取り込む機能（import）や中断した処理を再開する機能（resume）が存在しません。そのため、旧環境のバージョン、元の入力データ、対象リポジトリとの紐付け（束縛）をそのまま保持し、旧環境の公式ドキュメント（正本）に記載された再開条件に従って問題を解決します。BuildやCodeのキャンセル（cancel）、cleanupの準備・実行・再開（prepare/run/resume）などは、それぞれの呼び出し口（入口）が提供する機能の範囲内で利用します。Research、Think、Issueには共通のキャンセル機能が存在しないため、一括で取り消す手順は作成しません。また、OSの一時領域に保存されているデータであっても「不要なキャッシュ」として一括削除してはなりません（旧2・旧3・旧6） |
| 新scopingのcontextDir | `repository.txt` ファイルは、Gitの共通管理ディレクトリに紐付け（束縛）されます。`work/<task>/state.json`、ロックファイル（lock）、一時保存データ、および `research/` ディレクトリをそのまま保持します。これらは同じリポジトリ（repo）内の別作業ツリー（worktree）間で共有できますが、別々にクローンされたリポジトリ（別clone）の場合は異なる保存場所になります。また、ファイル内に記録されたリポジトリやコンテキスト保存ディレクトリ（contextDir）の絶対パスにも依存しているため、ディレクトリを移動させても自動的には修復されません。質問フィールド（question）に含まれる旧形式のセッションデータは読み込みを拒否するため、原本のデータを保持したまま、新環境のタスクに必要な参照情報のみを渡して再評価を行います。旧環境のワークフローJSONデータをそのまま読み替えて使用することはしません（[discovery](../../scripts/discovery.ts)、[保存・再開の正本](../../skills/scoping/references/session.md)） |
| 新implement/correctionのrunDir | development処理におけるデフォルトの保存場所は、ユーザーデータ領域内の `.local/share/dotagents/development/<Git共通管理ディレクトリのhash>/<Issue番号>/` です。ここには、要求仕様、隔離された作業ディレクトリ（隔離checkout）、初回実行結果、検証（verification）の設定・状態・ログファイル、プルリクエスト（PR）やCIの実行記録が保持されます。correction処理は、指定された実行データ保存用ディレクトリ（runDir）内に、実行回数、累積実行時間、アクティブ状態（active）、対象データのハッシュ値を保存します。新環境のコマンドラインツール（CLI）は、既存のdevelopment runDirの再利用、残ってしまったロックやアクティブ状態の自動解除、上限回数や時間のリセットを行いません。また、CLI側にはデータの移行機能、自動復旧機能、あるいは不要データを整理するcleanupの呼び出し口（入口）は用意されていません（[development](../../scripts/development.ts)、[input](../../scripts/input.ts)、[停止後の正本](../../scripts/README.md#結果と再実行)） |
| Git・未コミット作業と試行証拠 | 両方の作業ディレクトリ（checkout）におけるHEADの位置、各ブランチ（branch）、作業ツリー（worktree）との対応関係、インデックス登録済み（staged）・未登録（unstaged）・追跡対象外（untracked）・無視対象（ignored）の各ファイル、旧環境の未追跡ドキュメント、および実行時環境（runtime）の外部にあるデータ保存先について、内容を確認した上で保持します。新環境の `trial/evidence/` 内にあるメディアファイル、対象のバージョン情報、変更履歴（来歴）も保持し、これらを `trial/artifacts/` の再生成処理で代用することはしません。`trial/evidence/generated/` ディレクトリは実行ホストによって内容が自動的に置き換えられる領域であるため、移行比較に使用する既存のメディアファイルをそのまま上書きしてはなりません。また、試行用商品アプリケーションのローカルストレージ（localStorage）データは、オリジンやブラウザプロファイル側に保存された試行状態であるため、リポジトリのディレクトリを移動させてもデータは移送されません（[試行の保存区分](../../DEVELOPMENT.md#実装とテストの整理)、[商品仕様](../../README.md#提供する機能)） |

同じ `state.json` というファイル名であっても、システムが交わしている仕様の取り決め（契約）は旧環境と新環境で異なります。旧環境の実行時環境（runtime）が利用するSQLiteの所有権管理、新環境のdiscovery処理が行う保存用ロック（lock）、新環境のcorrection処理が行うリソース予約や対象ハッシュ値の管理には、互換性がありません。データ保存場所の統合、状態ファイル（state）の直接編集、あるいは旧環境での成功判定データをそのままコピーして流用するような操作は、移行手順に含めてはなりません。

## 事前確認から受入・復帰まで

以下に示している内容は、**将来的に移行案が関係者間で採択・合意された後に適用する判断の手順**です。今回はこれらの手順を実行しません。各作業段階の担当者は、確認した結果および未解決の課題を移行用のIssueやプルリクエスト（PR）に記録します。非公開の復元用記録には、必要となる実際の絶対パス、システムの登録先、データの保存場所を正確に記録します。一方で、公開されるドキュメントには相対パス、対象のコミット（commit）、確認によって得られた結論のみを掲載します。

| 段階 | 担当者が揃えるもの・進める条件 | 停止と戻り先 |
| --- | --- | --- |
| 1. 事前確認 | 移行担当者が新旧両方のHEADの位置と差分データを再取得し、本書に記載された内容との違いを確認します。ホスト環境の担当者は、実際にスキルが検出される元ディレクトリ、実行ファイル（bin）の解決先、自動実行処理（hook）の登録先とイベント種別、対象リポジトリ（repo）、認証を行う主体、すべてのデータ保存場所、ならびに現在進行中の実行プロセス（run）や作業ツリー（worktree）を特定します。あわせて、公開先のリポジトリおよびブランチの保護条件を確認します | 登録状況、所有者、進行中のデータ書き込み、あるいは過去の公開結果に不明な点が存在する場合は、切替処理を停止します。確認された事実の確認は調査プロセスへ、運用範囲や権限の設定に関する判断は依頼者の判断へ戻します |
| 2. 保全と準備 | 関係者は新規でプロセスを起動させない対象範囲を合意し、既存の実行プロセス（run）については旧環境のままで完了・取り消し・保留のいずれかの状態を確定させます。ファイルの変更内容、未追跡のドキュメント、無視対象（ignored）のデータ、実行時環境（runtime）、検証証拠、Gitの管理情報、システム登録設定を後から復元できるよう確実に保持します。稼働中のSQLiteデータベースファイルやGitリポジトリの一部だけをコピーしたものを、整合性の取れたバックアップとして扱ってはなりません。データ書き込みを完全に停止させた上で、復元が可能かどうかのテスト確認を行います。旧環境のソースコード、依存関係固定ファイル（lockfile）、および実行に必要な各種依存ライブラリも保管します | 単なる状態の複製（snapshot）や差分データ（diff）だけでは、未追跡ファイル、無視対象ファイル、外部保存場所の完全な保全にはなりません。所有者が不明である場合や復元が不可能な場合は、元の実行環境を保持したまま準備段階へ戻します。秘密情報については適切に管理された既存の保管手段を使用し、作業ディレクトリ（checkout）内に複製を作成してはなりません |
| 3. 候補環境での確認 | 旧環境の稼働環境とは別に、新環境の信頼できる作業ディレクトリ（checkout）を新しく用意する方針を選択します。対象リポジトリ（repo）の固定化に関する制約、共通チェック処理（check）における試行環境（trial）への依存関係、認証処理、スキルの表示、相対パスの参照関係、およびコマンドラインツール（CLI）の停止条件を確認します。残されている作業の実装、動作検証、ならびに採用に関する合意がすべて揃った段階で、切り替えの対象範囲と旧環境への戻し方を確定します | 他のリポジトリへ展開できない場合、旧環境で必要とされていた保証の代替案について合意が得られていない場合、あるいは過去の実行状態を必要とする処理を再開できない場合は、切替を行いません。別途作成するIssueでの実装作業、または対象範囲の再検討へ戻します |
| 4. 切替 | ホスト環境の登録担当者が、事前に承認された登録先および呼び出し口（入口）のみを移行候補のバージョンに向けます。旧環境の作業ディレクトリ（checkout）、保存状態、検証証拠、および復帰用の登録記録を保持し、同一のタスク（task）やリポジトリ（repo）に対して新旧両環境から同時にデータが書き込まれないようにします。新環境のタスクに対しては、これまでの合意内容、判断根拠、未解決事項への参照情報を渡し、新環境の評価基準に基づいて評価を行います | 具体的な登録方式がまだ決まっていない現時点においては、実行すべきコマンドを指定することはできません。新旧ツールの意図しない重複検出、旧hookの誤動作、予期しないリポジトリや公開主体の適用、データ保存場所の衝突などを検出した場合は、新規の起動を停止し、元の状態へ戻す（復帰）かの判断へ進みます |
| 5. 受入確認 | 運用担当者が、後述する受入確認項目について承認済みの対象範囲で確認を行います。検証担当者は既存のチェック処理（check）の実行結果を、独立評価担当者は要求仕様・ドキュメント・各種保証の不足がないかを、公開担当者は公開対象・公開主体・PRおよび必要なメディア表示を確認し、人間は最新のコード差分と未確認の範囲を確認します | 単に共通checkの実行に成功したという理由だけで、正規運用が可能であると判断してはなりません。機能実装の不足がある場合は修正および再検証へ、システムの登録や認証の問題であればホスト担当へ、要求範囲の変更であれば要求整理プロセス（scoping）へ戻します。受入確認に失敗した場合は、旧環境の資産を消去せずに処理を停止するか、復帰処理を行います |
| 6. 受入後の整理 | 新環境での安定した運用、ならびに過去の検証証拠が正しく参照・復元できることを確認した後に、旧資産を保管しておく期間、試行用資産の隔離先、および整理対象とするデータ範囲について、別途関係者間で合意を形成します | 受入確認が完了したことのみをもって、旧資産の削除やcleanupコマンドの実行が許可されたと解釈してはなりません。未完了の実行プロセス、未保存の検証証拠、あるいは対応するデータの存在しない投稿証明（receipt）が残っている場合は、整理作業を停止します |

### 受入で確認すること

- **入口**：事前に使用を許可したリポジトリ（repo）およびホスト環境において、意図したバージョンのスキルとコマンドラインツール（CLI）のみが呼び出され、パスの相対参照が正しく解決されることを確認します。旧環境の実行ファイル（bin）を残す場合は、それらの解決先が旧バージョンを指していること、および旧環境の自動実行処理（hook）が新環境の操作に対して誤って作用しないことを確認します。他のリポジトリへの対応を採用する場合は、そのリポジトリ上でも同様の動作確認を行います。
- **要求の引き継ぎ**：scoping処理において、事実確認の不足、人間からの回答待ち、合意の形成、Issueへの反映、および反映後の再読み込みが正しく行われていることを確認します。単なる提案レベルの内容である場合は、IssueやPRとして公開しません。すでに保存されている gate チェックの成功結果のみをもって「関係者の合意が得られた」と判断してはなりません。ドキュメントの変更のみを扱うIssueについても確認対象に含めます。
- **実装・停止**：合意済みのIssueに基づき、作業ツリーの隔離、共通チェック処理（check）、独立した評価、必要な自動修正、および修正後の再評価が正しく行われることを確認します。要求仕様の変更、コミットされていない未整理の変更が存在する状態（dirtyな入力）、既存の実行プロセス（run）の存在、ロック（lock）やアクティブ状態（active）の残存、制限回数の到達、あるいは環境障害が発生した際に、処理を「成功」として誤認しないことについて、既存の制御テストと対象バージョンの実行結果を照合して確認します。現在稼働している本番環境のデータを破壊する形でのテストは行いません。
- **公開・人への引き渡し**：公開が明示的に許可された試行ケースのみにおいて、Issue作成・PR作成・push・メディア添付を行う実行主体（公開主体）、対象となるブランチ（head/base）、最新のCI実行結果、必要なメディアファイルの表示状態、および人間に委ねられている承認作業の残項目を確認します。`--no-publish` オプションを指定してローカル環境で処理が成功したからといって、それを公開経路全体の成功を示す証拠としては扱いません。旧環境での下書きPR（draft PR）と新環境での通常のPRという形式の違いについても、採用判断の際に考慮します。
- **保持と復帰**：各種データの原本、コミットされていない作業ファイル、Git未追跡の資料、旧環境での処理停止状態、および検証証拠を正しく読み取れることを確認します。本番から隔離された環境で復元テストを行い、元のバージョン、登録先、保存場所の対応関係を確かめます。旧環境の実行時環境（runtime）のデータを互換性のある形式へ変換できたとは扱いません。

### 元へ戻す条件と方法

必要なリポジトリ（repo）でツールが起動しない場合、誤った公開主体や想定外の接続先へアクセスしてしまう場合、旧環境で必要とされていた重要な保証が欠落している場合、データ保存場所の衝突や検証証拠の欠落が発生している場合、あるいはあらかじめ合意した受入条件を満たさない場合は、新しい処理の実行を直ちに停止し、元の状態へ戻す（復帰する）判断を行います。その際、新環境側で作成された作業成果物、画像・動画などの各種メディア、消費されたAPI等の計算予算、および公開された結果データについても削除せずに保持します。新環境のコマンドラインツール（CLI）をシグナル（SIGINT/SIGTERM）で停止させる処理、および強制終了させた後に残っているプロセスを照合する手順については、[停止後の正本](../../scripts/README.md#結果と再実行)の記載に従います。単にロックファイル（lock）を削除しただけで「処理が安全に停止した」と判断してはなりません。

登録担当者は、事前に記録しておいた旧環境のスキル、実行ファイル（bin）、自動実行処理（hook）の参照先や設定パラメータを元の状態へ戻し、保管されていた旧バージョン、各種依存ライブラリ、および元のリポジトリ（repo）とデータ保存場所との対応関係を確認します。旧環境のローカルディレクトリ（checkout）を元の場所にそのまま保持する案を優先して推奨する理由は、絶対パスやファイルパスのハッシュ値を含んでいる実行状態データを別の場所に移し替えることなく、安全に元の状態へ復帰できる余地を残すためです。ただし、復帰作業が成功したかどうかについては、実機での確認が不可欠です。登録の仕組みや方式が明確になっていない段階で、`ln` によるシンボリックリンク作成、各種インストールコマンド、あるいはhookの解除コマンドなどを根拠なく作成・提示してはなりません。ホスト環境の担当者が登録の復元手順を具体的に作成・確定させるまでは、新環境への切り替えを行ってはならない（切替不可）とします。

旧環境で途中のまま停止している実行プロセスについては、旧環境の `workflows/README.md` に記載されている元入力データ、同一タスク（task）の単位、計算予算、データの所有権、および公開状態の照合結果に基づいて復帰できるかどうかを判断します。新環境の実行によって発生した変更データを旧環境の状態データ（state）へ直接流し込むような操作は行わず、引き継ぐべき変更点が存在する場合は、関係者間で合意された新しい作業として別途引き継ぎます。すでにGitHub上で公開されてしまったIssue、プルリクエスト（PR）、リモートへの送信（push）結果は、ローカルファイルの復元操作だけで取り消すことはできません。GitHub上の実際の発行状態と保留中の記録（pending記録）を突き合わせて確認し、情報の修正や公開の取り消しが必要な場合は、それを行うための適切な操作権限があるかを事前に確認します。送信に失敗したか結果が不明である公開処理を、別のタスク名に変更して安易に再送信してはなりません。

## 移行前に残る決定と実装

| 未解決事項 | 決める人・必要な成果 |
| --- | --- |
| 正規運用のrepo範囲と新旧保証の採否 | 依頼者および運用担当者。正規運用をこの試行用リポジトリ（repo）のみに限定するのか、あるいは他のリポジトリへも汎用化させるのかを決定します。また、旧環境のCode処理やcleanup処理、第三者監査、質問に対する回答待ち動作、公開意思の記録（intent）、および中断処理の再開保証を、どの程度まで残すのかについて合意を形成します |
| 実ホストの登録方法と復帰手順 | ホスト環境の登録担当者。スキルの検出元、環境変数PATH、および自動実行処理（hook）設定の現状を特定します。その上で、移行候補バージョンへの切り替え手順と、旧環境へ復帰させるための具体的な設定差分を、第三者がレビューできる形式で作成します。現在の試行リポジトリ（repo）には、汎用的なインストール用プログラム（installer）は用意されていません |
| 公開主体とOS対応 | 公開担当者。Issueの投稿、リモートへの送信（push）、PRの作成、ファイル添付のそれぞれにおける実行主体（アカウントやアプリ）とアクセス権限、GitHub Appに関する固定値設定の妥当性、macOS特有機能への依存関係の扱い、およびGitHub上のブランチ保護設定を確認します。なお、暗号鍵や制御コード自体の変更は、別のIssueで取り扱う範囲とします |
| 保存先・途中実行・互換性 | 実行担当者。実際に使用されているコンテキスト保存ディレクトリ（contextDir）、実行時環境（runtime）、生成成果物ディレクトリ（artifacts）、実行データ保存用ディレクトリ（runDir）を明確に特定します。その上で、旧環境のツールで解決すべき処理と、新環境のタスク（task）へ参照情報を引き継いで処理する作業とを明確に切り分けます。新環境側にはデータ取り込み（import）、自動復旧、ロック解除（lock解除）、あるいは旧環境の投稿証明（receipt）に対応した整理（cleanup）機能はありません。必要な機能があれば、仕様の策定から始めて合意を形成します |
| trialと正規ハーネスの検証分離 | 検証担当者。現行の検証処理（check、setup:e2e、capture）と試行環境（trial）が結合している状態を保ちながらデータを保存し、これらを分離した後の検証範囲と既存テストの引き継ぎ計画を別途Issueで定めます。関係者への共有なしに、テストの検出対象範囲を勝手に削減してはなりません |

これらの未解決事項が存在するからといって、本書の作成担当者が推測に基づいて不確実な情報を補ってよい理由にはなりません。これらの未解決事項は、実際の移行作業を一時停止・延期させるための必須条件として、そのまま記録に残します。

## 本書の検証と出典

今回の変更対象は、本Markdownファイルと [設計の入口](../design/README.md) のみです。現行のソースコード、設定ファイル、ガイド文書との照合を行い、相対リンクの正しさ、推奨する閲覧順序、責任範囲の抜け漏れ、旧環境の保証の過剰な引き継ぎがないか、ならびにデータの保全や復帰手順の不足がないかを確認します。独立評価を担当する者は文書の執筆者とは別の人物とし、指摘によって本文の文言が修正された場合は、関連するすべての箇所を改めて再照合します。共通の検証としては、実行ホスト側で既存の `bun run check` コマンドを実行します。文言の一致テストや専用の構造定義（スキーマ）は新たに追加しません。UIの画面変更や新規メディアファイルの要求は存在しないため、画面撮影の定義追加・変更、ならびに画像や動画の再生成は不要です。コードの静的照合結果や過去の [検証記録](../../trial/evidence/README.md) を、今回のホスト環境でのチェック結果、実際の移行完了結果、あるいは別の環境での実行成功結果として誤認させる報告を行ってはなりません。
